# Модель данных — часть 4: Продажа

Версия: 0.1
Статус: Черновик
Последнее обновление: 2026-10-23

Продолжение документов `04_модель_данных.md` (часть 1: справочники), `041_модель_данных.md` (часть 2: товары и склад), `042_модель_данных.md` (часть 3: закупка). Здесь описан контур продажи.

> **Ключевые принципы:**
> - **Два независимых контура.** Закупка и продажа не связаны напрямую. Пересечение — только через `stock`: закупка увеличивает `quantity`, продажа уменьшает.
> - **Продажа возможна при `stock.quantity > 0`.** Отдельного флага «оприходовано» нет — факт приёмки виден по остатку.
> - **Один заказ на продажу = один маркетплейс, одна валюта (RUB), одна история статусов.**
> - **Позиции заказа** — отдельная таблица (`salesOrderItems`), как в закупке.
> - **Возвраты** — отдельная сущность (`salesReturns`), не статус заказа. В MVP — минимальный набор полей, фаза 2 — расширение.
> - **Комиссия маркетплейса** — дефолт из `marketplaces`, фактическая — в заказе (правится вручную).
> - **Маркетплейс — финансовый посредник:** покупатель платит ему, нам перечисляется выплата (`payout*`).

## 4. Продажа

### 4.1. `salesOrders` — Заказы на продажу

**Назначение:** шапка заказа покупателя. Один заказ = один покупатель (или гость), один маркетплейс, одна валюта (RUB), одна история статусов.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `salesOrderId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `buyerId` | `INTEGER` | `REFERENCES buyers(buyerId)` | — | Покупатель. `NULL` — гостевая покупка (без регистрации) |
| `marketplaceId` | `SMALLINT` | `NOT NULL`, `REFERENCES marketplaces(marketplaceId)` | — | Маркетплейс (OZON, Avito, WB, YM, VK, SelfSite) |
| `marketplaceOrderId` | `VARCHAR(100)` | | — | Номер заказа на маркетплейсе (для сверки). Может быть `NULL` |
| `currencyId` | `SMALLINT` | `NOT NULL`, `REFERENCES currencies(currencyId)` | — | Валюта продажи (по умолчанию RUB) |
| `orderDate` | `DATE` | `NOT NULL` | — | Дата оформления заказа |
| `commissionRate` | `NUMERIC(5,4)` | `NOT NULL`, `CHECK (>= 0 AND <= 1)` | — | Фактическая комиссия маркетплейса (дефолт из `marketplaces`, правится вручную) |
| `commissionAmount` | `NUMERIC(12,2)` | `CHECK (commissionAmount >= 0)` | — | Сумма комиссии (`saleTotal × commissionRate`). Вычисляется при сохранении |
| `payoutAmount` | `NUMERIC(12,2)` | `CHECK (payoutAmount >= 0)` | — | Сумма, которую маркетплейс перечислит нам (`saleTotal − commissionAmount`). Вычисляется |
| `payoutStatus` | `VARCHAR(20)` | `NOT NULL`, `CHECK (IN ('pending','paid','adjusted'))` | `'pending'` | Статус выплаты: ожидается, выплачена, скорректирована (возврат) |
| `payoutDate` | `DATE` | | — | Дата фактической выплаты. Может быть `NULL` |
| `notes` | `TEXT` | | — | Заметки. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создан |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменён |

**Индексы:**
- `PRIMARY KEY (salesOrderId)`
- `INDEX (buyerId)` — для отчёта «покупки покупателя»
- `INDEX (marketplaceId)` — для отчёта «продажи по маркетплейсу»
- `INDEX (orderDate)` — для отчёта «продажи за период»
- `INDEX (payoutStatus)` — для отчёта «ожидаемые выплаты»
- `INDEX (marketplaceOrderId)` — для сверки с маркетплейсом

**Бизнес-правила:**
- `buyerId = NULL` — гостевая покупка. Покупатель не идентифицирован. Для аналитики «средний чек» такие заказы учитываются, для «LTV покупателя» — нет.
- `currencyId` — по умолчанию RUB (маркетплейсы работают в рублях). Поле есть на будущее (если появится продажа в другой валюте).
- `commissionRate` — дефолт из `marketplaces.defaultCommissionRate` при создании. Может быть изменён вручную (комиссии часто меняются).
- `commissionAmount` и `payoutAmount` — вычисляются при сохранении: `commissionAmount = saleTotal × commissionRate`, `payoutAmount = saleTotal − commissionAmount`. `saleTotal` = `SUM(salePrice × quantity)` по позициям.
- `payoutStatus`:
  - `pending` — заказ оформлен, выплата ожидается.
  - `paid` — маркетплейс перечислил деньги, `payoutDate` заполнена.
  - `adjusted` — выплата скорректирована (возврат, удержание). Сумма может отличаться от `payoutAmount`.
- `orderDate` — дата оформления заказа покупателем. Одна из ключевых дат для аналитики.

### 4.2. `salesOrderItems` — Позиции заказа на продажу

**Назначение:** строки заказа. Один товар + количество + цена продажи. При продаже — списание со склада.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `salesOrderItemId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `salesOrderId` | `INTEGER` | `NOT NULL`, `REFERENCES salesOrders(salesOrderId) ON DELETE CASCADE` | — | Заказ |
| `goodId` | `INTEGER` | `NOT NULL`, `REFERENCES goods(goodId) ON DELETE RESTRICT` | — | Товар |
| `quantity` | `INTEGER` | `NOT NULL`, `CHECK (quantity > 0)` | — | Количество проданных единиц |
| `salePrice` | `NUMERIC(12,2)` | `NOT NULL`, `CHECK (salePrice >= 0)` | — | Цена за единицу при продаже (в валюте заказа) |
| `costAtSale` | `NUMERIC(12,2)` | `CHECK (costAtSale >= 0)` | — | Себестоимость единицы на момент продажи (`stock.avgCostRub` на дату продажи). Для маржинальности. `NULL` — себестоимость неизвестна |
| `warehouseId` | `SMALLINT` | `NOT NULL`, `REFERENCES warehouses(warehouseId)` | — | С какого склада списан товар |
| `notes` | `TEXT` | | — | Заметки по позиции. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменена |

**Индексы:**
- `PRIMARY KEY (salesOrderItemId)`
- `INDEX (salesOrderId)` — для выборки позиций заказа
- `INDEX (goodId)` — для отчёта «продажи по товару»
- `INDEX (warehouseId)` — для отчёта «продажи со склада»

**Бизнес-правила:**
- `quantity > 0` — количество проданных единиц.
- `salePrice` — цена продажи за единицу (в валюте заказа).
- **`costAtSale`** — себестоимость единицы **на момент продажи** (`stock.avgCostRub`). Фиксируется, чтобы можно было посчитать маржинальность даже после того, как `avgCost` изменится следующими закупками. `NULL` — себестоимость неизвестна (товар импортирован без цены закупки). Для таких позиций маржинальность не считается.
- `warehouseId` — с какого склада списан товар. Для MVP — `main`. На фазе 2, если понадобится — можно добавить логику «списать сначала с main, потом с archive».
- **Списание со склада:** при создании позиции (или при смене статуса заказа на `collected`) — `stock.quantity` уменьшается на `quantity`. Проверка: `stock.quantity - stock.countOfRepair >= quantity` (нельзя продать то, что в подготовке).

### 4.3. `salesOrderStatusHistory` — История статусов заказа на продажу

**Назначение:** все переходы статусов заказа с датой. Текущий статус — последняя запись.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `historyId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `salesOrderId` | `INTEGER` | `NOT NULL`, `REFERENCES salesOrders(salesOrderId) ON DELETE CASCADE` | — | Заказ |
| `statusId` | `SMALLINT` | `NOT NULL`, `REFERENCES statuses(statusId)` | — | Статус (из `statuses`, где `statusType IN ('sale','common')`) |
| `statusDate` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда статус установлен |
| `comment` | `TEXT` | | — | Комментарий. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда запись создана (для аудита) |

**Индексы:**
- `PRIMARY KEY (historyId)`
- `INDEX (salesOrderId, statusDate)` — для выборки истории и определения текущего статуса
- `INDEX (statusId)` — для отчёта «сколько заказов в статусе X»

**Статусы заказа на продажу:**

| № | `statusName` | Что означает | Ключевая дата для анализа |
|---|---|---|---|
| 1 | `paid` | Покупатель оплатил заказ | **Дата оплаты** |
| 2 | `collected` | Заказ собран на складе, готов к отправке | — |
| 3 | `shipped` | Передан в доставку (маркетплейса или свою) | **Дата отправки** |
| 4 | `received` | Покупатель получил заказ | **Дата получения** |
| 5 | `refusal` | Покупатель отказался / вернул | **Дата отказа** |

**Бизнес-правила:**
- При создании заказа — запись `paid` (маркетплейс подтвердил оплату).
- При смене статуса — новая запись. Старые не удаляются.
- Текущий статус = последняя запись по `statusDate`.
- `refusal` — финальный статус для возврата. Детали возврата — в `salesReturns` (см. 4.4).

### 4.4. `salesReturns` — Возвраты по продажам

**Назначение:** фиксация возвратов. Отдельная сущность, не статус заказа. В MVP — минимальный набор полей; расширение (частичные возвраты, причины, компенсации) — фаза 2.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `returnId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `salesOrderId` | `INTEGER` | `NOT NULL`, `REFERENCES salesOrders(salesOrderId) ON DELETE RESTRICT` | — | Заказ |
| `returnDate` | `DATE` | `NOT NULL` | — | Дата возврата |
| `reason` | `VARCHAR(50)` | `NOT NULL`, `CHECK (IN ('customer_refusal','damaged','wrong_item','not_as_described','lost_in_return'))` | — | Причина возврата |
| `refundAmount` | `NUMERIC(12,2)` | `CHECK (refundAmount >= 0)` | `0` | Сумма, возвращённая покупателю (в валюте заказа) |
| `returnShippingCost` | `NUMERIC(12,2)` | `CHECK (returnShippingCost >= 0)` | `0` | Стоимость обратной доставки (если на нас) |
| `returnedToStock` | `BOOLEAN` | `NOT NULL` | `TRUE` | Товар вернулся на склад и доступен для продажи |
| `returnCondition` | `VARCHAR(20)` | `CHECK (IN ('new','used','damaged'))` | — | Состояние товара при возврате. `NULL` — если `returnedToStock = FALSE` |
| `warehouseId` | `SMALLINT` | `REFERENCES warehouses(warehouseId)` | — | На какой склад возвращён товар. `NULL` — если не возвращён |
| `notes` | `TEXT` | | — | Заметки. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменена |

**Индексы:**
- `PRIMARY KEY (returnId)`
- `INDEX (salesOrderId)` — для отчёта «возвраты по заказу»
- `INDEX (returnDate)` — для отчёта «возвраты за период»
- `INDEX (reason)` — для отчёта «причины возвратов»

**Бизнес-правила по причинам:**

| `reason` | Что произошло | `returnedToStock` | Компенсация | Убыток |
|---|---|---|---|---|
| `customer_refusal` | Покупатель передумал | `TRUE` (товар вернулся) | — | `refundAmount + returnShippingCost` |
| `damaged` | Товар повреждён | `TRUE`, `returnCondition = 'damaged'` | — | `refundAmount + returnShippingCost` |
| `wrong_item` | Пришёл не тот товар | `TRUE` | — | `refundAmount + returnShippingCost` |
| `not_as_described` | Не соответствует описанию | `TRUE` | — | `refundAmount + returnShippingCost` |
| `lost_in_return` | Потерян при обратной доставке | `FALSE` | **OZON компенсирует полную стоимость (как за покупку)** | Убытка нет (компенсация), товар списывается со склада |

**OZON при потере товара при возврате:** компенсирует полную стоимость продажи. В `salesReturns`: `returnedToStock = FALSE`, `refundAmount = 0`, `notes` — «потерян при возврате, компенсирован маркетплейсом». В `salesOrders`: `payoutStatus = 'paid'`, `payoutAmount` — полный, без удержаний.

**Возврат товара на склад (MVP):**
1. `salesOrders` → статус `refusal`.
2. `salesReturns` — запись с `returnedToStock = TRUE`, `warehouseId = main` (или другой), `returnCondition`.
3. `stock.quantity` увеличивается на количество возвращённого товара.
4. Если `returnCondition IN ('used','damaged')` — увеличивается `stock.countOfRepair` (товар требует подготовки перед повторной продажей).
5. `salesOrders.payoutStatus = 'adjusted'` — выплата скорректирована на `refundAmount`.

**Убыток по возврату** = `refundAmount + returnShippingCost`. На MVP фиксируем только прямые потери, без учёта будущей перепродажи.

**Для фазы 2:** частичные возвраты (не весь заказ, а часть позиций), возврат с компенсацией от маркетплейса, история состояний возврата.

## 4 ключевые даты для анализа (продажа)

| № | Событие | Где хранится | Как получить |
|---|---|---|---|
| 1 | Дата оплаты | `salesOrders.orderDate` (или `statusDate` статуса `paid`) | Поле / история |
| 2 | Дата сборки | `salesOrderStatusHistory` | `statusDate` статуса `collected` |
| 3 | Дата отправки | `salesOrderStatusHistory` | `statusDate` статуса `shipped` |
| 4 | Дата получения / отказа | `salesOrderStatusHistory` | `statusDate` статуса `received` / `refusal` |

**Аналитика:**
- Время от оплаты до отправки (`shipped − paid`) — скорость сборки.
- Время в пути (`received − shipped`) — логистика.
- Общее время заказа (`received − paid`).
- Процент возвратов (`COUNT(refusal) / COUNT(*)`).
- Средний чек (`AVG(saleTotal)`).
- Маржинальность (`saleTotal − commissionAmount − SUM(costAtSale × quantity)`) — только по позициям с `costAtSale IS NOT NULL`.

## Изменения в части 1 (`04_модель_данных.md`) — справочник `statuses`

С учётом продажи, итоговый набор:

| `statusName` | `statusType` | `sortOrder` | Где используется |
|---|---|---|---|
| `at_carrier` | `shipment` | 10 | Посылка: поступила в СД |
| `shipped` | `shipment` | 20 | Посылка: отправлена (закупка) / Заказ: передан в доставку (продажа) |
| `customs` | `shipment` | 30 | Посылка: на таможне |
| `out_for_delivery` | `shipment` | 40 | Посылка: в доставке (опц.) |
| `paid` | `sale` | 50 | Заказ на продажу: оплачен |
| `collected` | `sale` | 60 | Заказ на продажу: собран |
| `received` | `common` | 70 | Посылка: получена. Заказ на продажу: получен покупателем |
| `refusal` | `sale` | 80 | Заказ на продажу: отказ / возврат |

`statusType` — `'shipment'`, `'sale'`, `'common'`. `'purchase'` пока пуст (заказ — подсущность посылки, своей истории нет).

**Важно:** `shipped` используется и для посылки (закупка), и для заказа на продажу. `statusType` различает контекст. В `statuses` можно завести две записи с одинаковым `statusName = 'shipped'`, но разным `statusType` — либо одну с `'common'`. **Решение:** одна запись `shipped` с `statusType = 'common'` (используется в обоих контурах). Аналогично `received`.

**В `04_модель_данных.md` раздел 1.10** — обновить `UNIQUE (statusName)` → `UNIQUE (statusName, statusType)`, чтобы можно было иметь `shipped` для shipment и для sale отдельно (если понадобится). Пока — `common`.
