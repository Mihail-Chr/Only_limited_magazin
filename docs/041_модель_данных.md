## 2. Товары и склад

### 2.1. `goods` — Товары

**Назначение:** карточка товара. Один SKU = одна запись. Игра, сборник, стилбук, геймпад, фигурка — всё в одной таблице, различаются через `typeGoodId`.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `goodId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `goodName` | `VARCHAR(200)` | `NOT NULL`, `UNIQUE` | — | Полное название SKU: `Doom Eternal Deluxe Edition (PS4, EU)` |
| `baseGameName` | `VARCHAR(150)` | | — | Базовое название игры без издания/платформы: `Doom Eternal`. Для не-игровых товаров — `NULL` |
| `typeGoodId` | `SMALLINT` | `NOT NULL`, `REFERENCES typeGoods(typeGoodId)` | — | Тип товара: `game`, `bundle`, `steelbook`, `gamepad`, ... |
| `platformId` | `SMALLINT` | `REFERENCES platforms(platformId)` | — | Платформа. Обязательна для игр; `NULL` для универсальных аксессуаров |
| `relatedGameId` | `INTEGER` | `REFERENCES goods(goodId)` | — | Для аксессуаров/стилбуков — ссылка на игру, к которой относится. `NULL` для самостоятельных товаров |
| `publisherId` | `SMALLINT` | `REFERENCES publishers(publisherId)` | — | Издатель / производитель |
| `regionId` | `SMALLINT` | `REFERENCES regions(regionId)` | — | Регион выпуска |
| `editionId` | `SMALLINT` | `REFERENCES editionTypes(editionId)`, `DEFAULT 1` | `1` (Standard) | Тип издания |
| `firstReleaseYear` | `SMALLINT` | `CHECK (firstReleaseYear BETWEEN 1950 AND 2100)` | — | Год первого релиза игры в принципе (оригинал). Может быть `NULL` |
| `firstYearEdition` | `SMALLINT` | `CHECK (firstYearEdition BETWEEN 1950 AND 2100)` | — | Год выпуска **этой** версии/издания. Может быть `NULL` |
| `remakeYear` | `SMALLINT` | `CHECK (remakeYear BETWEEN 1950 AND 2100)` | — | Год ремейка, если это ремейк. Для ре-релизов (не ремейков) — `NULL` |
| `audience` | `SMALLINT` | `CHECK (audience IN (0, 6, 12, 16, 18))` | — | Возрастной рейтинг: 0 = нет ограничений. Может быть `NULL` |
| `ageRestricted` | `BOOLEAN` | `NOT NULL` | `FALSE` | Запрещён к продаже лицам младше 18 |
| `dataQuality` | `VARCHAR(10)` | `NOT NULL`, `CHECK (IN ('full','partial','minimal'))` | `'minimal'` | Качество данных: полные, частичные (нет цен), минимальные (только имя и платформа) |
| `barcode` | `VARCHAR(50)` | `UNIQUE` | — | Штрихкод (EAN-13, UPC). Строка цифр, вводится сканером или вручную. Опционально |
| `sku` | `VARCHAR(50)` | `UNIQUE` | — | Внутренний артикул. Опционально |
| `notes` | `TEXT` | | — | Заметки кладовщика / администратора. Опционально |
| `isActive` | `BOOLEAN` | `NOT NULL` | `TRUE` | Признак «товар активен» (снятые с продажи — `FALSE`) |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда запись создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда последний раз изменялась |

**Индексы:**
- `PRIMARY KEY (goodId)`
- `UNIQUE (goodName)` — каждое SKU имеет уникальное имя
- `UNIQUE (barcode)` — если barcode заполнен, он уникален
- `UNIQUE (sku)` — если sku заполнен, он уникален
- `INDEX (baseGameName)` — для поиска всех изданий игры
- `INDEX (platformId)` — для фильтрации по платформе
- `INDEX (typeGoodId)` — для фильтрации по типу
- `INDEX (relatedGameId)` — для поиска аксессуаров игры
- `INDEX (isActive)` — для фильтра «активные»

**Бизнес-правила:**
- **Признак сборника — `typeGoodId = 'bundle'`.** Флаг `isBundle` не используется. Состав сборника — в таблице `bundleItems`.
- `editionId` по умолчанию `1` (Standard). Запись с `editionId = 1` должна существовать в `editionTypes` при стартовом заполнении (первой вставляем Standard).
- `firstReleaseYear`, `firstYearEdition`, `audience` — **могут быть `NULL`** (для товаров, где информация утрачена или не применима).
- `firstReleaseYear` и `firstYearEdition` — **разные** события: оригинальный релиз и релиз конкретного издания. Пример: Need for Speed: Underground (2003) → Limited Run Edition (2005). Это позволяет видеть «волны популярности»: когда выходит новое издание, старые начинают дорожать.
- `remakeYear` — только для ремейков. Ре-релиз (переиздание) — это не ремейк, `remakeYear = NULL`.
- `barcode` и `sku` — опциональны, но если заполнены, должны быть уникальны.
- `notes` — опционально, свободный текст.

**Примеры записей:**

| goodName | baseGameName | typeGoodId | platformId | relatedGameId | editionId | firstReleaseYear | firstYearEdition | audience | dataQuality |
|---|---|---|---|---|---|---|---|---|---|
| Doom Eternal Deluxe Edition (PS4, EU) | Doom Eternal | game | PS 4 | NULL | Deluxe | 2020 | 2020 | 18 | full |
| Doom Eternal (Steelbook Без Игры) | Doom Eternal | steelbook | PS 4 | → Doom Eternal | Steelbook | 2020 | 2020 | NULL | full |
| Nintendo Switch Pro Controller: Sonic | NULL | gamepad | Switch 1 | NULL | Standard | NULL | NULL | NULL | full |
| Trine Ultimate Collection (NSW) | Trine | **bundle** | Switch 1 | NULL | Ultimate | 2009 | 2020 | 12 | full |
| The Banner Saga Trilogy (NSW) | The Banner Saga | **bundle** | Switch 1 | NULL | Standard | 2014 | 2018 | 12 | full |

### 2.2. `productGenres` — Жанры товара (M2M)

**Назначение:** связь многие-ко-многим между товарами и жанрами. Один товар — несколько жанров.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `productId` | `INTEGER` | `NOT NULL`, `REFERENCES goods(goodId) ON DELETE CASCADE` | — | Товар |
| `genreId` | `SMALLINT` | `NOT NULL`, `REFERENCES genres(genreId) ON DELETE RESTRICT` | — | Жанр |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда привязан |

**Индексы:**
- `PRIMARY KEY (productId, genreId)` — защита от дублей
- `INDEX (genreId)` — для обратного поиска «все товары с жанром X»

**Бизнес-правила:**
- Один товар — от 1 до N жанров. Для игр и сборников минимум 1 (заполняет кладовщик при приёмке).
- Нельзя привязать несуществующий жанр или товар (защита FK).
- Один и тот же жанр нельзя привязать дважды (защита PK).
- Для не-игровых товаров (стилбуки, геймпады) — жанры не применимы, записей нет.

### 2.3. `productLanguages` — Языки товара (M2M)

**Назначение:** связь многие-ко-многим между товарами и языками. Один товар — несколько языков.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `productId` | `INTEGER` | `NOT NULL`, `REFERENCES goods(goodId) ON DELETE CASCADE` | — | Товар |
| `languageId` | `SMALLINT` | `NOT NULL`, `REFERENCES languages(languageId) ON DELETE RESTRICT` | — | Язык |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда привязан |

**Индексы:**
- `PRIMARY KEY (productId, languageId)` — защита от дублей
- `INDEX (languageId)` — для обратного поиска «все товары на языке X»

**Бизнес-правила:**
- **При создании товара приложение автоматически привязывает English** (запись в `productLanguages` с `languageId` английского языка). Кладовщик при приёмке может добавить другие языки или удалить English, если его нет в данной версии.
- **В M2M-таблице нельзя поставить `DEFAULT` на `languageId`**: `DEFAULT` срабатывает при `INSERT`, а `INSERT` в M2M происходит только когда есть связь. Поэтому автопривязка English реализуется **на уровне приложения** (при создании товара — сразу `INSERT` в `productLanguages`). Если позже понадобится автопривязка на уровне БД — добавим триггер.
- Для игр и сборников — минимум 1 язык (обязательно, заполняет кладовщик).
- Для не-игровых товаров (стилбуки, геймпады) — языки не применимы, записей нет.
- Один и тот же язык нельзя привязать дважды (защита PK).

**Для фазы 2:** разделение на «язык интерфейса» / «язык субтитров» — через добавление поля `localizationType` в связку.

### 2.4. `bundleItems` — Состав сборника (M2M между товарами)

**Назначение:** связь многие-ко-многим между сборником и входящими в него играми. Один сборник — несколько игр, одна игра — может входить в разные сборники.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `bundleGoodId` | `INTEGER` | `NOT NULL`, `REFERENCES goods(goodId) ON DELETE CASCADE` | — | Товар-сборник (`typeGoodId = 'bundle'`) |
| `includedGoodId` | `INTEGER` | `NOT NULL`, `REFERENCES goods(goodId) ON DELETE RESTRICT` | — | Игра, входящая в сборник |
| `quantity` | `SMALLINT` | `NOT NULL`, `CHECK (quantity > 0)` | `1` | Количество экземпляров этой игры в сборнике |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда привязан |

**Индексы:**
- `PRIMARY KEY (bundleGoodId, includedGoodId)` — защита от дублей
- `INDEX (includedGoodId)` — для поиска «в какие сборники входит игра X»

**Бизнес-правила:**
- `bundleGoodId != includedGoodId` — сборник не может содержать сам себя.
- `bundleGoodId` должен иметь `typeGoodId = 'bundle'` (проверка в приложении).
- **Для заполнения `bundleItems` нужны записи в `goods` для каждой игры, входящей в сборник.** Если игра не продаётся отдельно — создать запись с `isActive = FALSE` (только для аналитики).
- Для MVP: таблица есть, но заполнение **не обязательно**. Достаточно того, что товар имеет `typeGoodId = 'bundle'`. Наполнение — фаза 2, когда понадобится аналитика «продажи по играм внутри сборников».
- Если `bundleItems` пуст для сборника — это не ошибка, а «состав неизвестен / не разобран».

### 2.5. `warehouses` — Склады (справочник)

**Назначение:** список физических/логических складов. Минимум 3: `main` (основной), `archive` (архив), `repair` (предпродажная подготовка).

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `warehouseId` | `SMALLSERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `warehouseName` | `VARCHAR(50)` | `NOT NULL`, `UNIQUE` | — | Название (`main`, `archive`, `repair`) |
| `sortOrder` | `SMALLINT` | `NOT NULL` | `100` | Порядок вывода |
| `isActive` | `BOOLEAN` | `NOT NULL` | `TRUE` | Признак «склад используется» |

**Индексы:**
- `PRIMARY KEY (warehouseId)`
- `UNIQUE (warehouseName)`

**Стартовые данные:** `main`, `archive`, `repair`. Пользователь может добавить свои (например, `reserved`, `transit`).

**Бизнес-правила:**
- `main` — основной склад, откуда идёт продажа.
- `archive` — для товаров, снятых с продажи, но физически имеющихся (коллекция, редкие экземпляры).
- `repair` — для товаров в предпродажной подготовке. Альтернатива `countOfRepair` (см. ниже — обсуждается).
- Склады можно добавлять, деактивировать (`isActive = FALSE`). Не удалять физически, если есть остатки.

### 2.6. `stock` — Остатки на складах

**Назначение:** остатки товаров на каждом складе. Одна запись на пару `(склад, товар)`. Физическое количество, количество в предпродажной подготовке, средневзвешенная себестоимость в трёх валютах.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `warehouseId` | `SMALLINT` | `NOT NULL`, `REFERENCES warehouses(warehouseId)` | — | Склад |
| `goodId` | `INTEGER` | `NOT NULL`, `REFERENCES goods(goodId) ON DELETE RESTRICT` | — | Товар |
| `quantity` | `INTEGER` | `NOT NULL`, `CHECK (quantity >= 0)` | `0` | Физическое количество на этом складе (включая `countOfRepair`) |
| `countOfRepair` | `INTEGER` | `NOT NULL`, `CHECK (countOfRepair >= 0 AND countOfRepair <= quantity)` | `0` | Количество единиц в предпродажной подготовке |
| `avgCostRub` | `NUMERIC(12,2)` | `CHECK (avgCostRub >= 0)` | — | Средневзвешенная себестоимость в RUB. `NULL` — цена неизвестна |
| `avgCostUsd` | `NUMERIC(12,2)` | `CHECK (avgCostUsd >= 0)` | — | Средневзвешенная себестоимость в USD. `NULL` — цена неизвестна |
| `avgCostEur` | `NUMERIC(12,2)` | `CHECK (avgCostEur >= 0)` | — | Средневзвешенная себестоимость в EUR. `NULL` — цена неизвестна |
| `lastExchangeRateDate` | `DATE` | | — | Дата курса, по которому пересчитано (для аудита) |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда запись создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда последний раз изменялась |

**Индексы:**
- `PRIMARY KEY (warehouseId, goodId)` — уникальная пара «склад + товар»
- `INDEX (goodId)` — для поиска «где лежит товар X»
- `INDEX (quantity)` — для отчёта «что заканчивается»
- `INDEX (countOfRepair)` — для отчёта «что в подготовке»

**Вычисляемые значения (не хранятся, вычисляются в запросах):**
- `availableForSale = quantity - countOfRepair` — доступно к продаже на этом складе

**Бизнес-правила:**
- `avgCost* = NULL` — цена закупки неизвестна. Не заменять на 0.
- При приёмке, если `avgCost* = NULL` и это **первая известная цена** — `avgCost` становится равной `landedCost` (без усреднения, т.к. старого значения нет).
- При приёмке, если `avgCost* IS NOT NULL` — пересчёт по формуле средневзвешенной (см. `02_бизнес-процессы.md`, раздел 3.3).
- Восстановление старых цен (вручную): администратор может напрямую установить `avgCost*` — это будет «текущая средняя», дальнейшие закупки пересчитают по формуле.
- При продаже — списание по средневзвешенной. Уменьшается `quantity`, `avgCost*` не меняется.
- `countOfRepair` — количество единиц, которые физически на складе, но недоступны для продажи (предпродажная подготовка, проверка, чистка). Семантика: `quantity` = всего физически (включая `countOfRepair`), `availableForSale = quantity - countOfRepair`.

**Пример:**

| warehouseId | goodId | quantity | countOfRepair | availableForSale | avgCostRub | avgCostUsd | avgCostEur |
|---|---|---|---|---|---|---|---|
| 1 (main) | 1 | 10 | 2 | 8 | 1375.00 | 15.00 | 13.80 |
| 1 (main) | 2 | 5 | 0 | 5 | NULL | NULL | NULL |
| 2 (archive) | 1 | 3 | 0 | 3 | 1200.00 | 13.00 | 12.00 |
| 3 (repair) | 1 | 2 | 2 | 0 | 1375.00 | 15.00 | 13.80 |

*Пояснение к примеру:*
- Товар 1 на складе `main`: 10 штук физически, из них 2 в подготовке → 8 доступно.
- Товар 1 на складе `archive`: 3 штуки (запас/коллекция), не продаётся.
- Товар 1 на складе `repair`: 2 штуки, обе в подготовке → 0 доступно. *(Здесь видно дублирование с `countOfRepair` — см. открытый вопрос ниже.)*

## ⚠️ Открытый вопрос: `countOfRepair` vs отдельный склад `repair`

Вы указали, что складов будет минимум 3, включая `archive`. Возникает вопрос: **как учитывать предпродажную подготовку?**

**Вариант A (текущий в документе):** `countOfRepair` — поле в `stock`, товар в подготовке лежит на том же складе, что и готовый. Склад `repair` не используется (или используется как «физическое место», но `countOfRepair` — главный учёт).

**Вариант B:** предпродажная подготовка — это **перемещение** товара на склад `repair`. Тогда `countOfRepair` не нужен: чтобы узнать «сколько в подготовке», смотрим `stock` для склада `repair`.

**Вариант C (гибрид):** `countOfRepair` — как в варианте A, но склад `repair` существует физически для «где лежат коробки». Тогда возможна рассинхронизация — не рекомендую.

**Плюсы A:** одно место учёта, простота.
**Плюсы B:** перемещение — это событие (можно отследить «когда поставлено на подготовку»), нет дублирования.
**Минусы A:** нет истории «когда ушло в подготовку».
**Минусы B:** нужно писать логику перемещений между складами.

**Рекомендация:** **Вариант A** для MVP (проще), с возможностью перейти на B на фазе 2. Но если `repair` как склад нужен — лучше сразу B, чтобы не переделывать. **Жду решения.**

**v0.1** (2026-10-22): часть 2 — товары и склад. Учтены: три года (`firstReleaseYear`, `firstYearEdition`, `remakeYear`), `isBundle` + `bundleItems`, `warehouse` (один склад).

**v0.2** (2026-10-22):
- **Убран `isBundle`** из `goods`. Признак сборника — `typeGoodId = 'bundle'` (в `typeGoods` добавлено значение `bundle`).
- **`notes`** — помечено как опциональное.
- **`productLanguages`** — добавлено бизнес-правило: при создании товара приложение автоматически привязывает English. Объяснено, почему нельзя `DEFAULT` в M2M.
- **`warehouses` + `stock`** — вместо одной таблицы `warehouse` теперь справочник складов (`main`, `archive`, `repair`) и таблица остатков `stock` с составным PK `(warehouseId, goodId)`.
- **Примеры для `bundleItems`** — расширены до 16 сборников из файла названий игр.
- **Открытый вопрос:** `countOfRepair` vs отдельный склад `repair` — нужно решение.
