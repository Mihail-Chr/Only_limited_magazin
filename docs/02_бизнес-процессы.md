# Бизнес-процессы

Версия: 0.3
Статус: Черновик
Последнее обновление: 2026-10-21

Документ описывает ключевые сценарии работы магазина: от закупки товара за рубежом до продажи конечному покупателю. Служит основой для проектирования модели данных и логики приложения.

---

## 1. Участники (акторы)

| Актор | Роль | Внутренний / внешний |
|---|---|---|
| **Менеджер по закупкам** | Создаёт заказы на закупку, взаимодействует с поставщиками и посредниками | Внутренний |
| **Кладовщик** | Принимает посылки, проверяет товар, отмечает количество готового к продаже | Внутренний |
| **Менеджер по продажам** | Обрабатывает заказы на маркетплейсах, комплектует и отправляет | Внутренний |
| **Поставщик (Seller)** | Продаёт нам товар за рубежом | Внешний |
| **Посредник / Форвардер** | Консолидирует посылки из разных магазинов, организует доставку | Внешний |
| **Служба доставки** | Транспортирует посылки. Компенсирует потери при частичной/полной утрате | Внешний |
| **Таможня** | Начисляет и принимает пошлины | Внешний |
| **Покупатель (Buyer)** | Приобретает товар у нас. Может быть «гостем» без регистрации | Внешний |
| **Маркетплейс** | Принимает заказы, платежи, доставляет, обрабатывает возвраты, перечисляет нам выплаты | Внешний |

## 2. Жизненный цикл заказа на закупку

**Триггер:** остаток на складе опустился ниже заданного уровня или появился новый товар для продажи.

**Статусы заказа:** `paid` → `collected` → `delivery` → `customs` → `received` → `on_warehouse`  
**Альтернативные финалы:** `lost` (полная потеря — раздел 7), `partially_received` (частичная потеря — раздел 7)

| Статус | Что означает |
|---|---|
| `paid` | Заказ оплачен поставщику |
| `collected` | Поставщик собрал товар, готов передать в доставку |
| `delivery` | Посылка в пути |
| `customs` | Посылка на таможне |
| `received` | Посылка получена нами физически |
| `on_warehouse` | Товар проверен, оприходован на склад, доступен для продажи |
| `partially_received` | Часть посылки получена, часть потеряна (см. раздел 7) |
| `lost` | Посылка полностью потеряна/отвергнута (см. раздел 7) |

**Шаги:**

1. Менеджер создаёт `PurchaseOrder` (поставщик, валюта, дата) и позиции (товар, количество, цена за единицу).
2. Заказ оплачивается. Статус → `paid`. (Статуса `draft` нет — заказ создаётся сразу оплаченным.)
3. Поставщик собирает и передаёт в доставку. Создаётся или обновляется `Shipment` с трек-номером. Статус → `collected`, затем `delivery`.
4. Посылка проходит таможню. Если начислена пошлина — фиксируется в `Shipment.customsDuty`. Статус → `customs`.
5. Посылка получена. Статус → `received`.
6. Кладовщик принимает товар (раздел 3). Статус → `on_warehouse` (или `partially_received`, если часть потеряна).

**Жёсткое правило:** **один `PurchaseOrder` всегда целиком помещается в одну `Shipment`.** Не может быть разбит на две посылки. Одна `Shipment` может содержать несколько `PurchaseOrder` (консолидация).

## 3. Приёмка на склад

**Триггер:** посылка физически прибыла.

### 3.1. Определения переменных

**Уровень позиции заказа (`PurchaseOrderItem`):**

| Переменная | Значение |
|---|---|
| `supplierPrice` | Цена за единицу у поставщика (в валюте заказа) |
| `quantityOrdered` | Заказанное количество |
| `quantityReceived` | Фактически полученное количество (`>= 0`) |

**Уровень посылки (`Shipment`):**

| Переменная | Значение |
|---|---|
| `deliveryCost` | Стоимость доставки всей посылки |
| `customsDuty` | Сумма таможенной пошлины по посылке |
| `totalShipmentValue` | Суммарная стоимость **принятых** позиций всех заказов в посылке: `Σ (supplierPrice × quantityReceived)` по позициям с `quantityReceived > 0` |

**Уровень склада (`Warehouse`):**

| Переменная | Значение |
|---|---|
| `qtyBefore` | Количество на складе до приёмки (`warehouse.quantity`) |
| `avgCostBefore` | Средневзвешенная себестоимость до приёмки (в целевой валюте) |
| `qtyAfter` | Количество после приёмки |

### 3.2. Расчёт landed cost (себестоимость единицы)

Доставка и пошлина распределяются **пропорционально стоимости принятых позиций**. Потерянные позиции (`quantityReceived = 0`) в распределении **не участвуют** — вся overhead ложится на принятые.

```
positionValue     = supplierPrice × quantityReceived
positionShare     = positionValue / totalShipmentValue
positionOverhead  = (deliveryCost + customsDuty) × positionShare
landedCostPerUnit = supplierPrice + (positionOverhead / quantityReceived)
```

**Пример (полная приёмка):**
- Посылка: 12 000 ₽ товаров, доставка 3000 ₽, пошлина 1500 ₽ → overhead 4500 ₽.
- Позиция A: 5 шт. × 1000 ₽ = 5000 ₽. Доля = 0.4167. Overhead = 1875 ₽. Landed cost = 1000 + 1875/5 = **1375 ₽/шт**.

**Пример (частичная потеря — раздел 7):**
- Посылка: позиции A (5×1000 ₽) и B (2×2000 ₽). Доставка 3000 ₽, пошлина 1500 ₽.
- Потеряна позиция B целиком (2 шт. не дошли). Принята только A.
- `totalShipmentValue` = 5000 ₽ (только A). Вся overhead 4500 ₽ ложится на A.
- Landed cost A = 1000 + 4500/5 = **1900 ₽/шт**. Компенсация от службы доставки за B — `supplierPrice × 2 = 4000 ₽` (без overhead).

### 3.3. Обновление средневзвешенной себестоимости (в трёх валютах)

Учёт ведётся в **RUB, USD, EUR**. Пересчёт — **по курсу на дату прихода посылки** из `exchangeRates`. Источник курсов — **ЦБ РФ** (для RUB); кросс-курсы USD/EUR считаем через RUB. Пополнение — автоматическое.

Для каждой валюты `C`:

```
avgCostAfter(C) = (qtyBefore × avgCostBefore(C) + quantityReceived × landedCostPerUnit(C))
                  / (qtyBefore + quantityReceived)

qtyAfter = qtyBefore + quantityReceived
```

В `warehouse` фиксируется `lastExchangeRateDate` — дата курса, по которому пересчитано (для аудита).

**Мультивалютность — только на складе.** В `PurchaseOrder` и `SalesOrder` валюта одна (`currencyId`). Три валюты в `warehouse` нужны для аналитики и переоценки цен в карточках на OZON.

### 3.4. Порядок действий кладовщика

1. Сверяет фактическое количество с заказанным. Расхождения фиксируются.
2. Проверяет товар. Если единица требует предпродажной подготовки — увеличивает `warehouse.countOfRepair` (раздел 5).
3. Запускает приёмку: расчёт landed cost (3.2) и обновление средневзвешенной себестоимости (3.3).
4. Статус заказа → `on_warehouse` (или `partially_received`, если часть позиций потеряна).

**Семантика `warehouse.quantity`:** физический остаток (включая единицы в подготовке). Доступно к продаже = `quantity − countOfRepair`.

## 4. Жизненный цикл заказа на продажу

**Триггер:** покупатель оформил заказ на маркетплейсе.

**Статусы заказа:** `paid` → `collected` → `delivery` → `received`  
**Альтернативный финал:** `refusal` (см. раздел 8)

| Статус | Что означает |
|---|---|
| `paid` | Покупатель оплатил заказ |
| `collected` | Заказ собран на нашем складе, готов к отправке |
| `delivery` | Передан в доставку |
| `received` | Покупатель получил заказ |
| `refusal` | Покупатель отказался или вернул |

### 4.1. Роль маркетплейса

Маркетплейс — не только канал продажи, но и **финансовый посредник, логистический оператор и обработчик возвратов**.

| Функция | Что делает маркетплейс | Как отражается в `SalesOrder` |
|---|---|---|
| Приём платежей | Покупатель платит маркетплейсу, не нам | `payoutAmount`, `payoutStatus`, `payoutDate` |
| Удержание комиссии | Забирает процент от продажи | `commissionRate`, `commissionAmount` |
| Доставка (последняя миля) | Логистика покупателю | `marketplaceOrderId` для сверки; свой трек — если логистика наша |
| Возвраты | Принимает и обрабатывает. При потере товара при возврате — **компенсирует полную стоимость (как за покупку)** | Раздел 8 |

### 4.2. Шаги

1. Появляется заказ с маркетплейса. Создаётся `SalesOrder` + позиции. Покупатель может быть «гостем» (`buyerId = NULL`).
2. Статус → `paid`. Рассчитывается `commissionAmount = saleTotal × commissionRate` (`commissionRate` берётся из `marketplaces` по умолчанию, правится вручную).
3. Комплектация: списание со склада. Статус → `collected`.
4. Отправка. Если у нас своя логистика — фиксируется трек-номер. Если маркетплейса — трек на стороне маркетплейса. Статус → `delivery`.
5. Покупатель получил заказ. Статус → `received`. `payoutStatus = pending`.
6. Маркетплейс перечисляет выплату → `payoutStatus = paid`, `payoutDate` заполняется.

## 5. Предпродажная подготовка

**Триггер:** при приёмке выявлено, что часть товара требует подготовки.

**Механика:**

1. Кладовщик увеличивает `warehouse.countOfRepair` на количество единиц, требующих подготовки.
2. Товар физически на складе, но недоступен для продажи: `availableForSale = quantity − countOfRepair`.
3. После подготовки кладовщик уменьшает `countOfRepair`.

`countOfRepair` — **не статус заказа**, а свойство склада.

---

## 6. Консолидация посылок

**Триггер:** нужно снизить стоимость доставки.

1. Несколько поставщиков отправляют товары посреднику.
2. Посредник консолидирует их в одну `Shipment`.
3. К `Shipment` привязываются все `PurchaseOrder`, чьи позиции вошли.
4. У `Shipment` фиксируются: трек-номер, страна отправки, `deliveryCost`, `customsDuty`.
5. Дальнейший путь — раздел 2.

**Правило связи:** 1 `PurchaseOrder` → 1 `Shipment` (жёстко). 1 `Shipment` → N `PurchaseOrder` (консолидация).

---

## 7. Потери посылки (Shipment reject / partial loss)

**Триггер:** посылка полностью или частично отвергнута таможней, уничтожена, потеряна или возвращена поставщику.

### 7.1. Полная потеря

Посылка не дошла целиком.

1. Создаётся запись в `shipmentLosses`:
   - `shipmentId` (FK)
   - `lossDate`
   - `reason` (`customs_rejected`, `destroyed`, `returned_to_seller`, ...)
   - `lossType = 'full'`
   - `lossAmountRub`, `lossAmountUsd`, `lossAmountEur` — полная стоимость **товаров** посылки (`Σ supplierPrice × quantityOrdered`), без overhead
   - `refundReceived*` — сколько удалось вернуть от поставщика/таможни (часто 0)
   - `notes`
2. Все `PurchaseOrder` этой посылки переводятся в статус `lost`.
3. Позиции **не приходуются на склад**.
4. **Убыток не распределяется** на себестоимость других товаров. Это отдельная статья расходов.

### 7.2. Частичная потеря

Посылка дошла не полностью: часть позиций принята, часть потеряна.

1. Создаётся запись в `shipmentLosses`:
   - `lossType = 'partial'`
   - `lossAmount*` — `Σ supplierPrice × (quantityOrdered − quantityReceived)` по потерянным позициям (без overhead)
   - `refundReceived*` — **компенсация от службы доставки = `supplierPrice` потерянных позиций** (без overhead)
   - `notes`
2. Принятые позиции приходуются на склад по обычной формуле (3.2), но **вся overhead (доставка + пошлина) распределяется только на принятые позиции** — потерянные в `totalShipmentValue` не участвуют. Это увеличивает landed cost принятых единиц.
3. `PurchaseOrder` переходит в `partially_received`, если принято хоть что-то; в `lost`, если не принято ничего.

### 7.3. Почему убыток не «размазывается» на другие покупки

Если распределить убыток на себестоимость оставшихся товаров, искажается экономика: товар X кажется рентабельным, но «тащит» на себе убыток от потерянной посылки. Вы не увидите, что направление убыточно. Отдельная статья `shipmentLosses` даёт честную картину для решений (сменить поставщика, отказаться от направления, изменить таможенную схему).

## 8. Возвраты по продаже (Sales refusal)

**Триггер:** покупатель отказался или вернул товар.

**Ключевое отличие от потери посылки:** товар **возвращается к нам** и может быть продан снова (возможно, по другой цене). Поэтому это не «чистый убыток», а «неудачная продажа + потенциальная перепродажа».

### 8.1. Товар вернулся на склад (MVP)

1. Создаётся запись в `salesReturns`:
   - `salesReturnId` (PK)
   - `salesOrderId` (FK)
   - `returnDate`
   - `reason` (`customer_refusal`, `damaged`, `wrong_item`, `not_as_described`, ...)
   - `refundAmount` — сумма, возвращённая покупателю
   - `returnShippingCost` — стоимость обратной доставки (если на нас)
   - `returnedToStock = true`
   - `returnCondition` (`new` / `used` / `damaged`) — влияет на возможность и цену перепродажи
   - `warehouseRestockDate` — когда товар вернулся в доступный остаток
2. `SalesOrder` переходит в статус `refusal`.
3. Товар возвращается в `warehouse.quantity`. `countOfRepair` увеличивается, если состояние требует подготовки.
4. **Убыток по возврату** = `refundAmount + returnShippingCost`. На MVP фиксируем только прямые потери, без учёта будущей перепродажи.
5. Маркетплейс корректирует `payoutAmount` — `SalesOrder.payoutStatus = adjusted`.

### 8.2. Товар потерян при возврате (OZON компенсирует)

Сценарий: покупатель вернул товар, но при обратной доставке он потерян.

- **OZON компенсирует полную стоимость продажи (как за покупку).** Для нас это **не убыток в деньгах** — выплата приходит в полном объёме.
- Товар **списывается со склада** (он физически не вернулся).
- В `salesReturns`: `returnedToStock = false`, `refundAmount = 0` (компенсация от OZON), `notes` — «потерян при возврате, компенсирован маркетплейсом».
- В `SalesOrder`: `payoutStatus = paid`, `payoutAmount` — полный, без удержаний.

**Правило:** убыток фиксируется только если фактическая компенсация меньше суммы, которую мы потеряли. Если OZON платит как за покупку — убытка нет, есть только списание товара.

## 9. Сводная таблица статусов

| Контур | Статусы | Уровень |
|---|---|---|
| Закупка | `paid` → `collected` → `delivery` → `customs` → `received` → `on_warehouse` / `partially_received` / `lost` | `PurchaseOrder` |
| Продажа | `paid` → `collected` → `delivery` → `received` / `refusal` | `SalesOrder` |

Единый справочник `statuses` с полем `statusType` (`purchase` / `sale`). История изменений — `purchaseOrderStatusHistory` и `salesOrderStatusHistory`.

## 10. Дополнительные сущности

| Сущность | Назначение |
|---|---|
| `exchangeRates` | История курсов валют (дата, из валюты, в валюту, курс, источник). Пополняется автоматически из ЦБ РФ. Нужна для пересчёта себестоимости и аналитики |
| `shipmentLosses` | Потери посылок (полные и частичные). Отдельная статья, не распределяется на себестоимость |
| `salesReturns` | Возвраты по продажам. Товар возвращается на склад (или списывается, если потерян), фиксируется убыток или компенсация |

## 11. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| `draft` для `PurchaseOrder` до оплаты | Не нужен. Заказ создаётся сразу в `paid` |
| Источник курсов валют | ЦБ РФ (для RUB), кросс-курсы USD/EUR через RUB. Автоматическое пополнение |
| Мультивалютность | Только в `warehouse` (RUB, USD, EUR). В заказах — одна валюта |
| Частичная потеря посылки | Overhead распределяется только на принятые позиции. Компенсация от службы доставки = `supplierPrice` потерянных |
| Потеря товара при возврате | OZON компенсирует полную стоимость. Убытка нет, товар списывается со склада |
| Отказы | Две отдельные таблицы: `shipmentLosses` (purchase) и `salesReturns` (sale) |
