# Бизнес-процессы

Версия: 0.1
Статус: Черновик
Последнее обновление: 2026-10-21

Документ описывает ключевые сценарии работы магазина: от закупки товара за рубежом до продажи конечному покупателю. Служит основой для проектирования модели данных и логики приложения.

---

## 1. Участники (акторы)

| Актор | Роль | Внутренний / внешний |
|---|---|---|
| **Менеджер по закупкам** | Создаёт заказы на закупку, взаимодействует с поставщиками и посредниками | Внутренний |
| **Кладовщик** | Принимает посылки, проверяет товар, отмечает количество готового к продаже | Внутренний |
| **Менеджер по продажам** | Обрабатывает заказы на маркетплейсах, комплектует и отправляет | Внутренний |
| **Поставщик (Seller)** | Продаёт нам товар за рубежом | Внешний |
| **Посредник / Форвардер** | Консолидирует посылки из разных магазинов, организует доставку | Внешний |
| **Служба доставки** | Транспортирует посылки | Внешний |
| **Таможня** | Начисляет и принимает пошлины | Внешний |
| **Покупатель (Buyer)** | Приобретает товар у нас | Внешний |
| **Маркетплейс** | Принимает заказы покупателей, перечисляет нам выплаты | Внешний |

---

## 2. Жизненный цикл заказа на закупку

**Триггер:** остаток на складе опустился ниже заданного уровня или появился новый товар для продажи.

**Статусы заказа:** `paid` → `collected` → `delivery` → `customs` → `received` → `on_warehouse`

| Статус | Что означает |
|---|---|
| `paid` | Заказ оплачен поставщику |
| `collected` | Поставщик собрал товар, готов передать в доставку |
| `delivery` | Посылка в пути (передана в службу доставки) |
| `customs` | Посылка на таможне |
| `received` | Посылка получена нами, физически прибыла |
| `on_warehouse` | Товар проверен, оприходован на склад, доступен для продажи |

**Шаги:**

1. Менеджер по закупкам создаёт заказ на закупку: поставщик, валюта, дата. Добавляет позиции (товар, количество, цена за единицу).
2. Заказ передаётся поставщику, оплачивается. Статус → `paid`.
3. Поставщик подтверждает сборку и передаёт посылку в доставку. Статус → `collected`, затем `delivery`. Создаётся или обновляется `Shipment` с трек-номером.
4. Посылка проходит таможню. Если начислена пошлина — фиксируется в `Shipment.customsDuty`. Статус → `customs`.
5. Посылка получена. Статус → `received`.
6. Кладовщик принимает товар (см. раздел 3). После приёмки статус → `on_warehouse`.

---

## 3. Приёмка на склад

**Триггер:** посылка физически прибыла.

**Шаги:**

1. Кладовщик сверяет фактическое количество товара с позициями заказов на закупку, привязанных к этой посылке.
2. Если есть расхождения — фиксируются (в MVP не блокируют процесс, но заносятся в примечание).
3. Товар проверяется. Если единица требует предпродажной подготовки (почистить, заменить коробку, устранить мелкий дефект) — увеличивается `warehouse.countOfRepair` на соответствующее количество.
4. **Расчёт landed cost.** Стоимость доставки и пошлины посылки распределяются между позициями пропорционально стоимости товара:
   ```
   landedCost(unit) = supplierPrice + (shipmentDeliveryCost + shipmentCustomsDuty) × (supplierPrice × quantity) / totalShipmentValue / quantity
   ```
   Для упрощения: сначала считается доля позиции в общей стоимости посылки, потом делится на количество единиц в позиции.
5. **Обновление средневзвешенной себестоимости** на складе:
   ```
   newAvgCost = (warehouse.quantity × warehouse.avgCost + receivedQty × landedCost) / (warehouse.quantity + receivedQty)
   warehouse.quantity = warehouse.quantity + receivedQty
   ```
6. После завершения приёмки статус заказа → `on_warehouse`.

**Результат:** товар на складе, себестоимость пересчитана, `warehouse.quantity` актуален.

## 4. Жизненный цикл заказа на продажу

**Триггер:** покупатель оформил заказ на маркетплейсе (OZON, Avito, VK, свой сайт).

**Статусы заказа:** `paid` → `collected` → `delivery` → `received` (или `refusal`)

| Статус | Что означает |
|---|---|
| `paid` | Покупатель оплатил заказ |
| `collected` | Заказ собран на нашем складе, готов к отправке |
| `delivery` | Заказ передан в доставку (маркетплейса или свою) |
| `received` | Покупатель получил заказ |
| `refusal` | Покупатель отказался или вернул заказ |

**Шаги:**

1. Появляется заказ с маркетплейса. Создаётся `SalesOrder`: покупатель (или «гость»), маркетплейс, дата. Добавляются позиции (товар, количество, цена).
2. Статус → `paid`.
3. Кладовщик или менеджер комплектует заказ: списывает товар со склада. Статус → `collected`.
4. Заказ отправляется. Если у нас своя логистика — фиксируется трек-номер (в MVP можно хранить в `SalesOrder.trackNumber`). Если логистика маркетплейса — трек хранится на стороне маркетплейса. Статус → `delivery`.
5. Покупатель получает заказ. Статус → `received`.
6. Если покупатель отказался — статус → `refusal`. Детальный учёт возвратов (возврат денег, причина, повторное размещение на складе) — фаза 2.

**Комиссия маркетплейса:** рассчитывается как `salePrice × commissionRate`. `commissionRate` берётся из справочника `marketplaces` по умолчанию и может быть переопределён в конкретном заказе (правится вручную, потому что комиссии часто меняются).

## 5. Предпродажная подготовка

**Триггер:** при приёмке выявлено, что часть товара требует подготовки.

**Шаги:**

1. Кладовщик увеличивает `warehouse.countOfRepair` на количество единиц, требующих подготовки.
2. Товар физически находится на складе, но не доступен для продажи. `warehouse.quantity` — это общее физическое количество, `countOfRepair` — «замороженная» часть. Доступно к продаже = `quantity − countOfRepair`.
3. Когда подготовка завершена, кладовщик уменьшает `countOfRepair` на соответствующее количество.
4. Товар становится доступен для продажи.

`countOfRepair` не является статусом заказа — это свойство склада.

---

## 6. Консолидация посылок

**Триггер:** нужно снизить стоимость доставки, объединив заказы от разных поставщиков.

**Шаги:**

1. После того как несколько поставщиков отправили товар посреднику, посредник консолидирует их в одну посылку.
2. Создаётся `Shipment`, к которому привязываются все заказы на закупку, чьи позиции в неё вошли.
3. У `Shipment` фиксируются: трек-номер, страна отправки, стоимость доставки, таможенная пошлина.
4. Далее — стандартный путь: `delivery` → `customs` → `received` → приёмка (раздел 3). При приёмке доставка и пошлина распределяются между **всеми** позициями **всех** привязанных заказов.

**Важно:** одна посылка → много заказов на закупку. Один заказ на закупку → может быть в одной посылке (в MVP — всегда одна посылка на заказ).

## 7. Сводная таблица статусов

| Контур | Статусы | Уровень |
|---|---|---|
| Закупка (Purchase Order) | `paid` → `collected` → `delivery` → `customs` → `received` → `on_warehouse` | Заказ |
| Продажа (Sales Order) | `paid` → `collected` → `delivery` → `received` / `refusal` | Заказ |

Статусы хранятся в едином справочнике `statuses` с полем `statusType` (`purchase` / `sale` / `common`). История изменений — в таблицах `purchaseOrderStatusHistory` и `salesOrderStatusHistory` (дата, статус, комментарий).
