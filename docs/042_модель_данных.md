# Модель данных — часть 3: Закупка

Версия: 0.4
Статус: Черновик
Последнее обновление: 2026-10-23

Продолжение документов `04_модель_данных.md` (часть 1: справочники) и `041_модель_данных.md` (часть 2: товары и склад). Здесь описан контур закупки.

> **Зафиксированные решения:**
> - **Один `PurchaseOrder` всегда целиком помещается в одну `Shipment`.** Одна `Shipment` может содержать несколько `PurchaseOrder` (консолидация). FK `shipmentId` в `purchaseOrders`.
> - **`countOfRepair` — Вариант A.** Поле в `stock`, товар в подготовке лежит на том же складе.
> - **Все суммы в закупке — в валюте заказа** (`currencyId` в `purchaseOrders`).
> - **Одна посылка = одна валюта.** Мультивалютных посылок нет.
> - **`landedCost*` не хранится в `purchaseOrderItems`.** Вычисляется при приёмке и сразу идёт в `stock.avgCost*`.
> - **`totalAmount` не хранится в `purchaseOrders`.** Вычисляется по позициям.
> - **Две истории статусов — по необходимости:** `purchaseOrderStatusHistory` (заказ) и `shipmentStatusHistory` (посылка). Это разные сущности с разными жизненными циклами, не дублирование.
> - **Поля дат в `shipments` не хранятся** — даты событий берутся из `shipmentStatusHistory` (`statusDate`).
> - **`quantityReceived`** — результат приёмки, хранится в позиции. История приёмок — фаза 2.
> - **4 ключевые даты для анализа:** `orderDate` (оплата), `at_svh` (поступление на СВХ), `shipped` (отправка shipment), `received` (получение).

## 3. Закупка

### 3.1. `purchaseOrders` — Заказы на закупку

**Назначение:** шапка заказа на закупку у зарубежного поставщика. Один заказ = один поставщик, одна валюта, одна посылка (в итоге).

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `purchaseOrderId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `sellerId` | `SMALLINT` | `NOT NULL`, `REFERENCES sellers(sellerId)` | — | Поставщик (у кого покупаем) |
| `currencyId` | `SMALLINT` | `NOT NULL`, `REFERENCES currencies(currencyId)` | — | Валюта заказа (валюта страны закупки: JPY, USD, EUR) |
| `orderDate` | `DATE` | `NOT NULL` | — | **Дата оплаты (начала заказа).** Всегда предоплата — заказ создаётся сразу оплаченным |
| `externalNumber` | `VARCHAR(50)` | | — | Номер заказа у поставщика. Может быть `NULL` |
| `shipmentId` | `INTEGER` | `REFERENCES shipments(shipmentId) ON DELETE RESTRICT` | — | Посылка, в которую целиком помещён заказ. `NULL` — пока не привязан |
| `notes` | `TEXT` | | — | Заметки. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создан |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменён |

**Индексы:**
- `PRIMARY KEY (purchaseOrderId)`
- `INDEX (sellerId)` — для отчёта «закупки по поставщику»
- `INDEX (currencyId)` — для валютной аналитики
- `INDEX (shipmentId)` — для обратного поиска «заказы в посылке»
- `INDEX (orderDate)` — для отчёта «закупки за период»

**Бизнес-правила:**
- `orderDate` — **дата оплаты (начала заказа).** Всегда предоплата, поэтому заказ создаётся сразу со статусом `paid`. Это одна из 4 ключевых дат для анализа.
- `currencyId` — валюта заказа. Все суммы в позициях — в этой валюте.
- `shipmentId` — `NULL`, пока заказ не привязан к посылке. При привязке — один заказ = одна посылка. Валюта заказа должна совпадать с валютой посылки.
- `externalNumber` — может быть `NULL`.
- Сумма заказа не хранится — вычисляется по позициям.

### 3.2. `purchaseOrderItems` — Позиции заказа на закупку

**Назначение:** строки заказа. Один товар + количество + цена за единицу.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `purchaseOrderItemId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `purchaseOrderId` | `INTEGER` | `NOT NULL`, `REFERENCES purchaseOrders(purchaseOrderId) ON DELETE CASCADE` | — | Заказ |
| `goodId` | `INTEGER` | `NOT NULL`, `REFERENCES goods(goodId) ON DELETE RESTRICT` | — | Товар |
| `quantityOrdered` | `INTEGER` | `NOT NULL`, `CHECK (quantityOrdered > 0)` | — | Заказанное количество |
| `quantityReceived` | `INTEGER` | `CHECK (quantityReceived >= 0 AND quantityReceived <= quantityOrdered)` | — | Фактически полученное количество. Заполняется при приёмке. `NULL` — ещё не принято |
| `supplierPrice` | `NUMERIC(12,2)` | `NOT NULL`, `CHECK (supplierPrice >= 0)` | — | Цена за единицу у поставщика (в валюте заказа) |
| `notes` | `TEXT` | | — | Заметки по позиции. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменена |

**Индексы:**
- `PRIMARY KEY (purchaseOrderItemId)`
- `INDEX (purchaseOrderId)` — для выборки позиций заказа
- `INDEX (goodId)` — для отчёта «закупки по товару»
- `INDEX (quantityReceived)` — для отчёта «что не принято»

**Бизнес-правила:**
- `quantityReceived` — `NULL`, пока приёмка не проведена. При приёмке заполняется. **История приёмок — фаза 2** (таблица `receipts`).
- `supplierPrice` — в валюте заказа.
- `landedCost*` не хранится — вычисляется при приёмке и сразу идёт в `stock.avgCost*`.
- При пересортице — `quantityReceived` корректируется по позициям.

### 3.3. `shipments` — Посылки

**Назначение:** физическая отправка. Одна посылка может содержать несколько заказов на закупку (консолидация). Имеет трек-номер, стоимость доставки, пошлину. **Даты событий — в `shipmentStatusHistory`, не в полях.**

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `shipmentId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `trackNumber` | `VARCHAR(100)` | | — | Трек-номер. Может быть `NULL`, пока не присвоен. **Не уникален** — у разных служб свои форматы |
| `currencyId` | `SMALLINT` | `NOT NULL`, `REFERENCES currencies(currencyId)` | — | Валюта посылки (для `deliveryCost` и `customsDuty`). Совпадает с валютой всех привязанных `purchaseOrders` |
| `deliveryCost` | `NUMERIC(12,2)` | `CHECK (deliveryCost >= 0)` | — | Стоимость доставки всей посылки (в валюте посылки). Может быть `NULL` |
| `customsDuty` | `NUMERIC(12,2)` | `CHECK (customsDuty >= 0)` | — | Сумма таможенной пошлины (в валюте посылки). Может быть `NULL` |
| `notes` | `TEXT` | | — | Заметки. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменена |

**Индексы:**
- `PRIMARY KEY (shipmentId)`
- `INDEX (trackNumber)` — для поиска по треку (без `UNIQUE`)
- `INDEX (currencyId)` — для валютной аналитики

**Бизнес-правила:**
- `trackNumber` — `NULL`, пока не присвоен. Не уникален.
- `currencyId` — валюта посылки. Все `purchaseOrders` в посылке имеют ту же валюту.
- **Поля дат (`shipDate`, `customsDate`, `receiveDate`) отсутствуют.** Даты событий — в `shipmentStatusHistory` (`statusDate`). Каждый статус имеет свою дату, отдельные поля не нужны.
- `deliveryCost`, `customsDuty` — в валюте посылки. Могут быть `NULL`.

---

### 3.4. `shipmentStatusHistory` — История статусов посылки

**Назначение:** все переходы статусов посылки с датой. Текущий статус — последняя запись. **Здесь же хранятся даты событий** (отправка, таможня, получение) — отдельные поля дат в `shipments` не нужны.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `historyId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `shipmentId` | `INTEGER` | `NOT NULL`, `REFERENCES shipments(shipmentId) ON DELETE CASCADE` | — | Посылка |
| `statusId` | `SMALLINT` | `NOT NULL`, `REFERENCES statuses(statusId)` | — | Статус (из `statuses`, где `statusType = 'shipment'`) |
| `statusDate` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда статус установлен (дата события) |
| `comment` | `TEXT` | | — | Комментарий. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда запись создана (для аудита) |

**Индексы:**
- `PRIMARY KEY (historyId)`
- `INDEX (shipmentId, statusDate)` — для выборки истории посылки и определения текущего статуса
- `INDEX (statusId)` — для отчёта «сколько посылок в статусе X»

**Бизнес-правила:**
- Статусы посылки: `formed` (сформирована), `shipped` (отправлена, присвоен трек-номер), `customs` (на таможне), `in_transit` (в пути после таможни), `received` (получена).
- **Дата отправки (`shipDate` для анализа) = `statusDate` статуса `shipped`.**
- **Дата получения (`receiveDate` для анализа) = `statusDate` статуса `received`.**
- **Дата прохождения таможни = `statusDate` статуса `customs`.**
- При смене статуса — новая запись. Старые не удаляются.
- Текущий статус = последняя запись по `statusDate`.

---

### 3.5. `purchaseOrderStatusHistory` — История статусов заказа

**Назначение:** все переходы статусов **заказа** с датой. Текущий статус — последняя запись. Здесь хранится **дата поступления на СВХ** (статус `at_svh`).

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `historyId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `purchaseOrderId` | `INTEGER` | `NOT NULL`, `REFERENCES purchaseOrders(purchaseOrderId) ON DELETE CASCADE` | — | Заказ |
| `statusId` | `SMALLINT` | `NOT NULL`, `REFERENCES statuses(statusId)` | — | Статус (из `statuses`, где `statusType IN ('purchase','common')`) |
| `statusDate` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда статус установлен (дата события) |
| `comment` | `TEXT` | | — | Комментарий. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда запись создана (для аудита) |

**Индексы:**
- `PRIMARY KEY (historyId)`
- `INDEX (purchaseOrderId, statusDate)` — для выборки истории заказа и определения текущего статуса
- `INDEX (statusId)` — для отчёта «сколько заказов в статусе X»

**Бизнес-правила:**
- При создании заказа — сразу запись со статусом `paid` (дата = `orderDate`).
- Статусы заказа: `paid` → `sent_to_carrier` → `at_svh` → (ждёт консолидации) → `on_warehouse` / `partially_received` / `lost`.
- **Дата поступления на СВХ (`svhDate` для анализа) = `statusDate` статуса `at_svh`.**
- При смене статуса — новая запись. Старые не удаляются.
- Текущий статус = последняя запись по `statusDate`.

### 3.6. Связь `purchaseOrders` ↔ `shipments`

Реализована через FK `shipmentId` в `purchaseOrders`:
- Один `PurchaseOrder` → одна `Shipment` (жёсткое правило).
- Одна `Shipment` → много `PurchaseOrder` (обратный FK).

### 3.7. `shipmentLosses` — Потери посылок

**Назначение:** фиксация потерь посылок (полных и частичных), а также брака и некомплекта. Отдельная статья расходов, **не распределяется** на себестоимость других товаров.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `lossId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `shipmentId` | `INTEGER` | `NOT NULL`, `REFERENCES shipments(shipmentId) ON DELETE RESTRICT` | — | Посылка |
| `lossType` | `VARCHAR(10)` | `NOT NULL`, `CHECK (IN ('full','partial'))` | — | Тип потери: полная / частичная |
| `lossDate` | `DATE` | `NOT NULL` | — | Дата фиксации потери |
| `reason` | `VARCHAR(50)` | `NOT NULL`, `CHECK (IN ('customs_rejected','destroyed','returned_to_seller','lost_in_transit','defect','incomplete'))` | — | Причина: отказ таможни, уничтожение, возврат поставщику, потеря в пути, брак, некомплект |
| `lossAmount` | `NUMERIC(12,2)` | `NOT NULL`, `CHECK (lossAmount >= 0)` | — | Сумма потери (в валюте посылки) |
| `refundReceived` | `NUMERIC(12,2)` | `CHECK (refundReceived >= 0)` | `0` | Сколько удалось вернуть (в валюте посылки) |
| `notes` | `TEXT` | | — | Заметки. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменена |

**Индексы:**
- `PRIMARY KEY (lossId)`
- `INDEX (shipmentId)` — для отчёта «потери по посылке»
- `INDEX (lossDate)` — для отчёта «потери за период»
- `INDEX (lossType)` — для фильтра «полные / частичные»
- `INDEX (reason)` — для отчёта «причины потерь»

**Бизнес-правила по причинам:**

| `reason` | `lossType` | Что произошло | Компенсация (`refundReceived`) |
|---|---|---|---|
| `customs_rejected` | `full` или `partial` | Таможня не пропустила | От поставщика/таможни (часто 0) |
| `destroyed` | `full` или `partial` | Уничтожено | От поставщика/ТК |
| `returned_to_seller` | `full` или `partial` | Возвращено поставщику | Частичный возврат оплаты |
| `lost_in_transit` | `full` или `partial` | Потеряно в пути | От службы доставки |
| `defect` (брак) | `partial` | Товар пришёл, но непригоден к продаже | **От ТК по цене закупки** (`supplierPrice`) |
| `incomplete` (некомплект) | `partial` | Не хватает единиц | **От ТК по цене закупки** (`supplierPrice`) |

**Пересортица** — **не loss**. При пересортице количество по позициям корректируется (`quantityReceived`), сумма единиц совпадает. Компенсация не нужна, `shipmentLosses` не создаётся.

**Распределение overhead — три случая:**

1. **Нормальная приёмка (всё принято):** `deliveryCost + customsDuty` распределяются на **все** позиции **всех** заказов в посылке пропорционально стоимости (`supplierPrice × quantityReceived`).
2. **Частичная потеря (принято хоть что-то):** overhead распределяется **только на принятые** позиции. Потерянные не участвуют в `totalShipmentValue` — вся overhead ложится на принятые. Компенсация от ТК = `supplierPrice` потерянных (без overhead).
3. **Полная потеря (не принято ничего):** overhead **не распределяется**. Вся потеря (товары + overhead) — отдельная статья в `shipmentLosses`. Все `purchaseOrders` в посылке → `lost`.

**Убыток = `lossAmount − refundReceived`.** Фиксируется как отдельная статья, не распределяется на себестоимость.

## 4 ключевые даты для анализа (как получить)

| № | Событие | Где хранится | Как получить |
|---|---|---|---|
| 1 | Дата оплаты (начало заказа) | `purchaseOrders.orderDate` | Поле |
| 2 | Дата поступления на СВХ | `purchaseOrderStatusHistory` | `statusDate` статуса `at_svh` |
| 3 | Дата отправки shipment | `shipmentStatusHistory` | `statusDate` статуса `shipped` |
| 4 | Дата получения товара | `shipmentStatusHistory` | `statusDate` статуса `received` |

**Аналитика без справочника СД:**
- Время от оплаты до СВХ (`svhDate − orderDate`) — скорость поставщика.
- Время от СВХ до отправки shipment (`shipDate − svhDate`) — скорость консолидации.
- Время в пути (`receiveDate − shipDate`) — логистика (без разбивки по СД).
- Общее время заказа (`receiveDate − orderDate`).

**Когда появится справочник СД (`carriers`) — фаза 2:** разбивка по службам, сравнение скорости, автоматическое обновление статусов через API трекинга.
