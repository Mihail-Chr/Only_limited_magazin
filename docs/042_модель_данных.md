# Модель данных — часть 3: Закупка

Версия: 0.1
Статус: Черновик
Последнее обновление: 2026-10-22

Продолжение документов `04_модель_данных.md` (часть 1: справочники) и `041_модель_данных.md` (часть 2: товары и склад). Здесь описан контур закупки.

> **Зафиксированные решения:**
> - **Один `PurchaseOrder` всегда целиком помещается в одну `Shipment`.** Одна `Shipment` может содержать несколько `PurchaseOrder` (консолидация). Реализуется через FK `shipmentId` в `purchaseOrders` (nullable, пока посылка не создана).
> - **`countOfRepair` — Вариант A.** Поле в `stock`, товар в подготовке лежит на том же складе. Отдельный склад `repair` — физическое место, но учёт через `countOfRepair`.
> - **Все суммы в закупке — в валюте заказа** (`currencyId` в `purchaseOrders`). Доставка и пошлина — тоже в валюте заказа (см. открытый вопрос про мультивалютные посылки ниже).

## 3. Закупка

### 3.1. `purchaseOrders` — Заказы на закупку

**Назначение:** шапка заказа на закупку у зарубежного поставщика. Один заказ = один поставщик, одна валюта, один статус, одна посылка (в итоге).

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `purchaseOrderId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `sellerId` | `SMALLINT` | `NOT NULL`, `REFERENCES sellers(sellerId)` | — | Поставщик (у кого покупаем) |
| `currencyId` | `SMALLINT` | `NOT NULL`, `REFERENCES currencies(currencyId)` | — | Валюта заказа (валюта страны закупки: JPY, USD, EUR) |
| `orderDate` | `DATE` | | — | Дата заказа. Может быть `NULL` (если утрачена) |
| `externalNumber` | `VARCHAR(50)` | | — | Номер заказа у поставщика. Может быть `NULL` |
| `shipmentId` | `INTEGER` | `REFERENCES shipments(shipmentId) ON DELETE RESTRICT` | — | Посылка, в которую целиком помещён заказ. `NULL` — пока не привязан |
| `totalAmount` | `NUMERIC(12,2)` | `CHECK (totalAmount >= 0)` | — | Сумма всех позиций (`Σ supplierPrice × quantityOrdered`) в валюте заказа. Вычисляется при сохранении |
| `notes` | `TEXT` | | — | Заметки. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создан |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменён |

**Индексы:**
- `PRIMARY KEY (purchaseOrderId)`
- `INDEX (sellerId)` — для отчёта «закупки по поставщику»
- `INDEX (currencyId)` — для валютной аналитики
- `INDEX (shipmentId)` — для обратного поиска «заказы в посылке»
- `INDEX (orderDate)` — для отчёта «закупки за период»

**Бизнес-правила:**
- `currencyId` — валюта заказа. **Все денежные суммы в этом заказе и его позициях — в этой валюте** (supplierPrice, доставка, пошлина).
- `shipmentId` — `NULL`, пока заказ не привязан к посылке. При привязке — один заказ = одна посылка (жёсткое правило).
- `totalAmount` — вычисляется как `Σ (supplierPrice × quantityOrdered)` по позициям. Хранится для быстрого доступа к сумме заказа.
- `orderDate`, `externalNumber` — могут быть `NULL` (если информация утрачена). Это не блокирует работу.
- Статус заказа — не хранится в `purchaseOrders` напрямую. **Текущий статус** — последняя запись в `purchaseOrderStatusHistory` по `statusDate`. Это позволяет видеть историю переходов и «откаты» (если понадобятся).

### 3.2. `purchaseOrderItems` — Позиции заказа на закупку

**Назначение:** строки заказа. Один товар + количество + цена за единицу.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `purchaseOrderItemId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `purchaseOrderId` | `INTEGER` | `NOT NULL`, `REFERENCES purchaseOrders(purchaseOrderId) ON DELETE CASCADE` | — | Заказ |
| `goodId` | `INTEGER` | `NOT NULL`, `REFERENCES goods(goodId) ON DELETE RESTRICT` | — | Товар |
| `quantityOrdered` | `INTEGER` | `NOT NULL`, `CHECK (quantityOrdered > 0)` | — | Заказанное количество |
| `quantityReceived` | `INTEGER` | `CHECK (quantityReceived >= 0 AND quantityReceived <= quantityOrdered)` | — | Фактически полученное количество. Заполняется при приёмке. `NULL` — ещё не принято |
| `supplierPrice` | `NUMERIC(12,2)` | `NOT NULL`, `CHECK (supplierPrice >= 0)` | — | Цена за единицу у поставщика (в валюте заказа) |
| `landedCostRub` | `NUMERIC(12,2)` | `CHECK (landedCostRub >= 0)` | — | Себестоимость единицы с учётом доставки и пошлины, в RUB. Заполняется при приёмке. `NULL` — не рассчитано |
| `landedCostUsd` | `NUMERIC(12,2)` | `CHECK (landedCostUsd >= 0)` | — | То же в USD. `NULL` — не рассчитано |
| `landedCostEur` | `NUMERIC(12,2)` | `CHECK (landedCostEur >= 0)` | — | То же в EUR. `NULL` — не рассчитано |
| `notes` | `TEXT` | | — | Заметки по позиции. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменена |

**Индексы:**
- `PRIMARY KEY (purchaseOrderItemId)`
- `INDEX (purchaseOrderId)` — для выборки позиций заказа
- `INDEX (goodId)` — для отчёта «закупки по товару»
- `INDEX (quantityReceived)` — для отчёта «что не принято»

**Бизнес-правила:**
- `quantityReceived` — `NULL`, пока приёмка не проведена. При приёмке заполняется (может быть меньше `quantityOrdered` при частичной потере; может быть равно).
- `landedCost*` — заполняется при приёмке по формуле из `02_бизнес-процессы.md` (раздел 3.2). Для потерянных позиций (`quantityReceived = 0`) — `NULL` (не приходуются).
- `supplierPrice` — в валюте заказа (`purchaseOrders.currencyId`).
- **Позиции не удаляются** после приёмки. `ON DELETE CASCADE` только для случая, если заказ удаляется целиком (что не рекомендуется — лучше `isActive`/`status`).

### 3.3. `shipments` — Посылки

**Назначение:** физическая отправка. Одна посылка может содержать несколько заказов на закупку (консолидация). Имеет трек-номер, стоимость доставки, пошлину, даты.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `shipmentId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `trackNumber` | `VARCHAR(100)` | `UNIQUE` | — | Трек-номер. Может быть `NULL`, если ещё не присвоен |
| `currencyId` | `SMALLINT` | `NOT NULL`, `REFERENCES currencies(currencyId)` | — | Валюта посылки (для `deliveryCost` и `customsDuty`) |
| `shipDate` | `DATE` | | — | Дата отправки. Может быть `NULL` |
| `receiveDate` | `DATE` | | — | Дата фактического получения. Может быть `NULL` |
| `deliveryCost` | `NUMERIC(12,2)` | `CHECK (deliveryCost >= 0)` | — | Стоимость доставки всей посылки (в валюте посылки). Может быть `NULL`, если неизвестна |
| `customsDuty` | `NUMERIC(12,2)` | `CHECK (customsDuty >= 0)` | — | Сумма таможенной пошлины (в валюте посылки). Может быть `NULL` |
| `notes` | `TEXT` | | — | Заметки. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменена |

**Индексы:**
- `PRIMARY KEY (shipmentId)`
- `UNIQUE (trackNumber)` — если трек заполнен, он уникален
- `INDEX (shipDate)` — для отчёта «посылки за период»
- `INDEX (receiveDate)` — для отчёта «полученные посылки»

**Бизнес-правила:**
- `trackNumber` — `NULL`, пока не присвоен. При присвоении — уникален.
- `currencyId` — валюта посылки. **Для MVP предполагаем, что все `purchaseOrders` в одной посылке имеют одну валюту** (совпадает с валютой посылки). Если это не так — см. открытый вопрос ниже.
- `deliveryCost`, `customsDuty` — в валюте посылки. Могут быть `NULL`, если информация утрачена (например, старые посылки).
- `receiveDate` — заполняется при фактическом получении (до приёмки на склад).

### 3.4. Связь `purchaseOrders` ↔ `shipments`

Реализована через FK `shipmentId` в `purchaseOrders`. Отдельная промежуточная таблица **не нужна**, потому что:
- Один `PurchaseOrder` → одна `Shipment` (жёсткое правило).
- Одна `Shipment` → много `PurchaseOrder` (обратный FK).

**Ограничение:** `UNIQUE (purchaseOrderId)` уже есть (PK). Дополнительно — `shipmentId` в `purchaseOrders` не может быть изменён на другую посылку после привязки? Это бизнес-правило, проверяется в приложении (или триггером). В MVP — просто `UPDATE` при необходимости (если ошиблись).

### 3.5. `purchaseOrderStatusHistory` — История статусов заказа на закупку

**Назначение:** все переходы статусов заказа с датой. Текущий статус — последняя запись.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `historyId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `purchaseOrderId` | `INTEGER` | `NOT NULL`, `REFERENCES purchaseOrders(purchaseOrderId) ON DELETE CASCADE` | — | Заказ |
| `statusId` | `SMALLINT` | `NOT NULL`, `REFERENCES statuses(statusId)` | — | Статус (из `statuses`, где `statusType IN ('purchase','common')`) |
| `statusDate` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда статус установлен |
| `comment` | `TEXT` | | — | Комментарий. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда запись создана (для аудита) |

**Индексы:**
- `PRIMARY KEY (historyId)`
- `INDEX (purchaseOrderId, statusDate)` — для выборки истории заказа и определения текущего статуса
- `INDEX (statusId)` — для отчёта «сколько заказов в статусе X»

**Бизнес-правила:**
- При создании заказа — сразу запись со статусом `paid` (без `draft`).
- При смене статуса — новая запись. Старые не удаляются.
- Текущий статус = последняя запись по `statusDate` для данного `purchaseOrderId`.
- `statusId` должен иметь `statusType IN ('purchase', 'common')` (проверка в приложении).
- Для `purchaseOrder` допустимы статусы: `paid`, `collected`, `delivery`, `customs`, `received`, `on_warehouse`, `partially_received`, `lost`.

### 3.6. `shipmentLosses` — Потери посылок

**Назначение:** фиксация потерь посылок (полных и частичных). Отдельная статья расходов, **не распределяется** на себестоимость других товаров.

| Поле | Тип | Ограничения | По умолчанию | Описание |
|---|---|---|---|---|
| `lossId` | `SERIAL` | `PRIMARY KEY` | автоинкремент | Уникальный идентификатор |
| `shipmentId` | `INTEGER` | `NOT NULL`, `REFERENCES shipments(shipmentId) ON DELETE RESTRICT` | — | Посылка |
| `lossType` | `VARCHAR(10)` | `NOT NULL`, `CHECK (IN ('full','partial'))` | — | Тип потери: полная / частичная |
| `lossDate` | `DATE` | `NOT NULL` | — | Дата фиксации потери |
| `reason` | `VARCHAR(50)` | `NOT NULL` | — | Причина: `customs_rejected`, `destroyed`, `returned_to_seller`, `lost_in_transit`, ... |
| `lossAmount` | `NUMERIC(12,2)` | `NOT NULL`, `CHECK (lossAmount >= 0)` | — | Сумма потери (в валюте посылки) — `Σ supplierPrice × (quantityOrdered − quantityReceived)` по потерянным позициям |
| `refundReceived` | `NUMERIC(12,2)` | `CHECK (refundReceived >= 0)` | `0` | Сколько удалось вернуть от поставщика/таможни/службы доставки (в валюте посылки) |
| `notes` | `TEXT` | | — | Заметки. Опционально |
| `createdAt` | `TIMESTAMP` | `NOT NULL` | `NOW()` | Когда создана |
| `updatedAt` | `TIMESTAMP` | | — | Когда изменена |

**Индексы:**
- `PRIMARY KEY (lossId)`
- `INDEX (shipmentId)` — для отчёта «потери по посылке»
- `INDEX (lossDate)` — для отчёта «потери за период»
- `INDEX (lossType)` — для фильтра «полные / частичные»

**Бизнес-правила:**
- `lossAmount` — в валюте посылки (`shipments.currencyId`). Для полной потери = `Σ supplierPrice × quantityOrdered` по всем позициям всех заказов в посылке. Для частичной = `Σ supplierPrice × (quantityOrdered − quantityReceived)` по потерянным позициям.
- `refundReceived` — компенсация. Для частичной потери от службы доставки = `supplierPrice` потерянных позиций (без overhead). Может быть 0.
- **Убыток = `lossAmount − refundReceived`.** Фиксируется как отдельная статья, не распределяется на себестоимость.
- При полной потере: все `purchaseOrders` в посылке → статус `lost`. Позиции **не приходуются** на склад.
- При частичной потере: `purchaseOrders` → `partially_received` (если принято хоть что-то) или `lost` (если не принято ничего). Принятые позиции приходуются по обычной формуле, **overhead распределяется только на принятые** (потерянные не участвуют в `totalShipmentValue`).

## ⚠️ Открытый вопрос: мультивалютные посылки

Вы указали: «цена закупки, доставка и tax рассчитываются в валюте страны закупки». Это работает, если **все заказы в одной посылке — в одной валюте**.

Но возможна ситуация: заказ у японского поставщика (JPY) и заказ у американского (USD) консолидируются в одну посылку. Тогда `deliveryCost` и `customsDuty` — в какой валюте?

**Варианты:**

**A. Одна валюта на посылку.** Для MVP предполагаем, что все `purchaseOrders` в посылке имеют одну валюту (совпадает с `shipments.currencyId`). Если консолидация разных валют — редкость, можно пересчитать вручную при создании посылки. Просто, но ограничивает.

**B. Валюта каждой позиции.** `deliveryCost` и `customsDuty` распределяются между заказами пропорционально их стоимости, каждый заказ получает свою долю **в своей валюте** (пересчёт по курсу на дату). Сложно, но честно.

**C. Валюта посылки — отдельная.** `shipments.currencyId` — валюта, в которой фактически оплачена доставка/пошлина (например, RUB). При приёмке пересчёт в валюту каждого заказа. Ещё сложнее.

**Рекомендация для MVP — A.** Если в посылке разные валюты — это редкий случай, можно разбить на две посылки или пересчитать вручную. На фазе 2 — перейти на B, если понадобится.

**Жду решения.** Если A — оставляем как есть. Если B/C — нужно добавить поля.
