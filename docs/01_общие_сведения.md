# Общие сведения о проекте

Версия: 0.3
Статус: Черновик
Последнее обновление: 2026-10-22

---

## 1. Название

**Only_limited_magazin** — система учёта товаров и аналитики продаж для виртуального магазина игр, аксессуаров и коллекционных изданий.

---

## 2. Контекст

Магазин **уже ведёт деятельность**. Товары закупаются за рубежом, консолидируются в посылки через посредников и доставляются в Россию. Продажи идут через OZON и другие маркетплейсы. Ассортимент — игры для PC, PlayStation, Xbox, Nintendo Switch, Sega и ретро-платформ; аксессуары; коллекционные и ограниченные издания; сборники из нескольких игр.

**Текущее состояние учёта:**

- Остатки товара, выставленного на OZON, **оцифрованы** (Excel, личные заметки, выгрузка с OZON).
- Информация о **входящих ценах, номерах заказов и датах поставки в большинстве случаев утрачена** и восстановлению не подлежит. Именно это и стало причиной создания системы.
- Часть характеристик товара **не заполнена** — OZON не требует всех полей, которые нужны нам (издание, регион, жанр, язык и т.д.). Их придётся заполнять вручную.
- Есть товар, который **физически на складе, но не оцифрован вообще**.
- Продажи и закупки **не останавливаются** на время внедрения системы — они идут параллельно с наполнением базы.

Система создаётся не «с нуля на пустом месте», а **встраивается в работающий бизнес** с частично потерянными данными.

---

## 3. Цель проекта

**Главная цель:** создать программу-приложение для учёта товаров и аналитики продаж.

**Задача минимум (MVP):**

1. **Количественный учёт — приоритет №1.** Знать, сколько единиц каждого товара есть на складе, сколько в предпродажной подготовке, сколько продано, сколько закуплено.
2. **Наполнение справочника товаров и склада** — параллельно с продолжающимися продажами и закупками. Процесс займёт не один день.
3. **Упрощённые закупка и продажа** — прямой поток, без возвратов и частичных потерь.
4. **Работа с неполными данными** — там, где данных нет (цены закупки, номера заказов, даты), система работает, а не падает. Но **характеристики товара** (жанр, издание, регион, год выпуска, год первого релиза) кладовщик **обязан** заполнить при приёмке — на коробке эта информация всегда есть.

**Задача максимум (в перспективе):** полноценная аналитика маржинальности, интеграция с API маркетплейсов, прогнозирование закупок.

## 4. Границы проекта

### 4.1. Что входит в MVP

**Справочники:**
- Товары (`goods`), платформы, жанры, языки, издания, регионы, типы товаров, валюты, маркетплейсы, статусы, поставщики, покупатели, курсы валют.

**Склад:**
- Количественный учёт: `quantity`, `countOfRepair`.
- Себестоимость в трёх валютах (RUB, USD, EUR) — **опционально**: если известна, заполняется; если нет — `NULL`.
- Возможность добавлять товары на склад «вручную» (для неоцифрованных позиций) и импортировать существующие остатки.

**Закупка (упрощённая):**
- `PurchaseOrder` + позиции.
- `Shipment` с трек-номером, стоимостью доставки, пошлиной (в валюте закупки).
- Приёмка на склад с расчётом landed cost (если известны цены) или без него (если цены утрачены).
- Статусы: `paid` → `collected` → `delivery` → `customs` → `received` → `on_warehouse`.
- **Без** частичных потерь, **без** reject-сценариев.

**Продажа (упрощённая):**
- `SalesOrder` + позиции.
- Маркетплейс, комиссия, выплаты.
- Статусы: `paid` → `collected` → `delivery` → `received`.
- **Без** возвратов (`refusal`).

**Отчёты (базовые):**
- Остатки на складе.
- Продажи (за период, по маркетплейсу, по товару).
- Закупки (за период, по поставщику).

### 4.2. Что НЕ входит в MVP (фаза 2+)

| Функция | Причина отложения |
|---|---|
| Возвраты по продажам (`salesReturns`) | Усложняет модель и UI; на старте важнее количественный учёт |
| Частичные потери посылок (`shipmentLosses`) | Редкий сценарий; в MVP посылка считается либо «дошла», либо «не дошла» |
| Полный разбор сборников (`bundleItems`) | Таблица в модели будет, но наполнение — позже |
| Мультивалютность в заказах (не только в складе) | MVP: одна валюта на заказ (валюта страны закупки / RUB для продажи) |
| Интеграция с API маркетплейсов | Требует согласований и OAuth; после запуска учёта |
| Прогнозирование закупок, авто-пополнение | Требует накопленных данных |
| Личный кабинет покупателя | Учёт внутренний, покупатели не работают с системой напрямую |
| Бухгалтерская отчётность (1С, налоги) | Отдельный контур, вне ядра |
| Разделение интерфейсов и прав доступа | На старте — один пользователь выполняет все роли |

## 5. Пользователи и роли

**На MVP — один человек выполняет все роли.** Разделения интерфейсов и прав доступа нет. Но роли **выделяются в модели данных** (у заказов есть «автор», у действий — «кто сделал»), чтобы в будущем можно было разграничить.

| Роль | Что делает | Приоритет для MVP |
|---|---|---|
| **Администратор** | Отвечает за работоспособность системы, добавление/изменение полей в БД, управление справочниками, технические операции | **Обязательно** |
| **Владелец магазина** | Смотрит аналитику, принимает решения о закупках и ценах | Обязательно (часто = администратор) |
| **Менеджер по закупкам** | Создаёт заказы на закупку, ведёт поставщиков, меняет статусы закупок | Обязательно |
| **Кладовщик** | Принимает посылки, оприходует товар, **обязательно заполняет характеристики товара** (жанр, издание, регион, год выпуска, год первого релиза), отмечает `countOfRepair`, отпускает товар по продажам | Обязательно |
| **Менеджер по продажам** | Обрабатывает заказы с маркетплейсов, комплектует, отправляет | Обязательно |

**Почему администратор — отдельная роль:** кто-то должен отвечать за схему БД, справочники, миграции. В MVP это, скорее всего, тот же человек, что владелец, но роль фиксируется явно — чтобы в будущем не путать «бизнес-решение» и «техническое изменение».

## 6. Работа с неполными данными (режим миграции)

Ключевая особенность MVP: **данные приходят грязными и неполными**, а работать надо уже сейчас. Принципы:

### 6.1. Два типа полей: обязательные и «восстановимые»

**Характеристики товара — обязательны для игр.** Кладовщик при приёмке **обязан** заполнить:
- жанр (хотя бы один),
- издание (`editionId`),
- регион (`regionId`),
- год выпуска (`firstYearEdition`),
- год первого релиза (`firstReleaseYear`).

На коробке эта информация всегда есть. Если поле не заполнено — товар не может быть оприходован (или попадает в `dataQuality = 'minimal'` с явным предупреждением).

Для **аксессуаров** (геймпады, стилбуки) эти поля не применимы — они `NULL`, и это нормально.

**Цены и даты закупок — восстанавливаемые.** Если цена закупки утрачена — `warehouse.avgCostRub = NULL`. Не ставим `0`, не «угадываем». Если дата заказа неизвестна — `PurchaseOrder.orderDate = NULL`.

### 6.2. Флаг качества данных у товара

В `goods` — поле `dataQuality`:

| Значение | Что означает |
|---|---|
| `full` | Все обязательные поля заполнены, цены известны |
| `partial` | Характеристики заполнены, но цены закупки отсутствуют (типично для импортированных остатков) |
| `minimal` | Заполнены только название и платформа; остальное — заглушки (временное состояние, требует доработки) |

Фильтр в отчётах: «показывать только `full`» — для маржинальности. «Показывать все» — для количественного учёта.

### 6.3. Два способа наполнения склада

1. **Импорт** — загрузка текущих остатков OZON из CSV/Excel. Товары создаются с `dataQuality = 'partial'` (цены неизвестны). Количество фиксируется.
2. **Ручной ввод** — для товаров, которых нет в OZON (неоцифрованный склад, новые поступления).

Оба способа работают параллельно с обычными закупками и продажами.

### 6.4. Режим «только количественный учёт»

Пока цены закупки не восстановлены:
- **Количественный учёт работает полностью** — это задача минимум.
- **Маржинальность по товарам с `avgCost = NULL` не считается** — отчёт показывает «нет данных».
- **Цены продажи запоминаются** — для будущей аналитики, когда появятся цены закупки.
- Когда поступает новая закупка с известной ценой, `avgCost` заполняется через средневзвешенную. Если это первая известная цена — она становится средней (`avgCost = landedCostPerUnit`). Это позволяет «перетереть» старые `NULL` по мере поступления новых данных.

### 6.5. Восстановление старых цен

Если известно, что товар закупался по некой цене (например, из старых накладных или памяти), администратор может **вручную установить `avgCost`** для товара. Это будет «текущая средняя», и дальнейшие закупки будут пересчитывать её по стандартной формуле. Точность исторической аналитики по таким товарам будет ограничена, но количественный учёт и будущая маржинальность — корректны.

## 7. Мультивалютность

**При закупке** все три компонента — закупочная цена, доставка и **пошлина** — учитываются **в валюте страны закупки** (валюта `PurchaseOrder`). Логика: пошлина зависит от стоимости товара в валюте, а рублёвый эквивалент — производная. `exportTax` всегда оплачивает служба доставки (включён в стоимость доставки или выставляется отдельно), `importTax` (таможенная пошлина) — фиксируется в `Shipment` в валюте закупки.

**При приёмке на склад** значения пересчитываются в три валюты склада (RUB, USD, EUR) по курсу ЦБ РФ на дату прихода. В `warehouse` хранятся `avgCostRub`, `avgCostUsd`, `avgCostEur` — для аналитики и переоценки цен на карточках OZON.

**При продаже** — одна валюта (по умолчанию RUB; определяется маркетплейсом).

**Зачем три валюты на складе:** сравнивать цены закупок в разных странах (рубль слабеет — долларовые закупки дороже), вовремя менять цены на OZON, видеть динамику себестоимости в твёрдой валюте.

**Списание себестоимости при продаже** — по **средневзвешенной**. FIFO/LIFO не используем: для магазина с большим количеством мелких партий средневзвешенная проще и устойчивее.

## 8. Технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| OLTP-СУБД | **PostgreSQL** | Стандарт для транзакционных систем: внешние ключи, `CHECK`-ограничения, надёжность, зрелость |
| Аналитика (локально) | **DuckDB** | Колоночная СУБД, работает поверх тех же данных, быстрая на агрегатах. Мост к ClickHouse |
| Аналитика (перспектива) | **ClickHouse** | Когда объём данных вырастет — аналитический контур переедет сюда |
| Схема БД (визуализация) | **DrawDB** (локально) | ER-диаграммы с экспортом в PostgreSQL |
| Документация | **Markdown** + **Git** | Версионирование, рендер на GitHub, ревью через Pull Request |

**Принцип:** OLTP — в PostgreSQL, OLAP — в DuckDB/ClickHouse. Не смешивать.

## 9. Принципы проектирования

1. **Справочники — отдельно от транзакций.** Платформы, жанры, издания, регионы — в таблицах с `sortOrder` и `isActive`, а не в `CHECK`/`ENUM`.
2. **M2M — через промежуточные таблицы.** Жанры, языки, сборники — через junction с составным PK и FK.
3. **Имена — в camelCase.** `purchaseOrderId`, `avgCostRub`, `genreId`.
4. **Деньги — `NUMERIC`, не `FLOAT`.** Точность важнее скорости.
5. **Заказы — две таблицы, а не одна.** Разные поля, разные контрагенты, разные жизненные циклы.
6. **NULL — это «неизвестно», а не «ноль».** Не заменять отсутствующие данные суррогатами. Но характеристики товара — обязательны для игр.
7. **Аудит — обязателен.** `createdAt`, `updatedAt` везде, где есть изменения. История статусов — отдельными таблицами.
8. **Работать с неполными данными — это фича, а не баг.** Система должна быть полезна с первого дня, даже если половина цен пуста.

## 12. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Стартовое состояние данных | Магазин работает, часть данных утрачена, часть не оцифрована |
| Задача минимум | Количественный учёт + наполнение склада + упрощённые закупка/продажа |
| Характеристики игр (жанр, издание, регион, год выпуска, год первого релиза) | **Обязательны**, заполняет кладовщик при приёмке. На коробке всегда есть |
| Цены и даты закупок | Могут быть `NULL` — «неизвестно». Не заменять нулём |
| Флаг качества данных | `dataQuality` у товара: `full` / `partial` / `minimal` |
| Восстановление старых цен | Вручную установить `avgCost`; дальнейшие закупки пересчитают по средневзвешенной |
| Возвраты, частичные потери | Фаза 2 (в MVP — только прямые потоки) |
| Роли | Администратор, владелец, менеджер по закупкам, кладовщик, менеджер по продажам. Разделения интерфейсов нет |
| Валюта закупки | Одна — валюта страны закупки (цена, доставка, **пошлина**) |
| Валюты склада | Три: RUB, USD, EUR. Пересчёт по курсу ЦБ на дату прихода |
| Курсы валют | ЦБ РФ, автоматическое пополнение, таблица `exchangeRates` |
| Списание себестоимости | Средневзвешенная (moving average). FIFO/LIFO не используем |
| Стек | PostgreSQL (OLTP) + DuckDB (OLAP локально) + ClickHouse (перспектива) |
| `draft` для заказов | Не нужен — заказ создаётся сразу в `paid` |

## 13. Открытые вопросы (для фазы 2+)

1. **Списание по средневзвешенной и историческая точность.** При восстановлении старых цен вручную средневзвешенная даст приблизительную маржинальность по старым продажам. Это приемлемо для MVP; для точной исторической аналитики — фаза 2 (FIFO по партиям).
2. **Товары без цены закупки.** Если `avgCost = NULL`, а товар продаётся — в отчётах «нет данных», не портим средние. Восстановление — вручную или через новые закупки.
3. **Интеграция с каталогами игр.** Для фазы 6: RAWG (простой API, огромная база), IGDB (глубже метаданные), MobyGames (ретро). В MVP — только ручной ввод.
