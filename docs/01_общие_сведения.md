# Общие сведения о проекте

Версия: 1.0
Статус: Черновик
Последнее обновление: 2026-10-23

---

## 1. Название

**Only_limited_magazin** — система учёта товаров и аналитики продаж для виртуального магазина игр, аксессуаров и коллекционных изданий.

---

## 2. Контекст

Магазин **уже ведёт деятельность**. Товары закупаются за рубежом (площадки: eBay US/EU, Amazon JP/US/DE, Play-Asia, CDJapan и др.), консолидируются в посылки через посредников, доставляются в Россию. Продажи идут через OZON, Avito, WB, YM, VK и собственный сайт (SelfSite). Ассортимент — игры для PC/PlayStation/Xbox/Nintendo Switch/Sega и ретро-платформ, аксессуары, коллекционные и ограниченные издания, сборники.

**Текущее состояние учёта:**

- Остатки товара, выставленного на OZON, **оцифрованы** (Excel, выгрузка с OZON).
- Информация о **входящих ценах, номерах заказов и датах поставки в большинстве случаев утрачена**.
- Часть характеристик товара **не заполнена** — кладовщик заполняет вручную при приёмке (жанр, издание, регион, год выпуска).
- Есть товар, **физически на складе, но не оцифрован вообще**.
- Продажи и закупки **не останавливаются** на время внедрения.

Система встраивается в работающий бизнес с частично потерянными данными.

---

## 3. Цель проекта

**Главная цель:** создать программу-приложение для учёта товаров и аналитики продаж.

**Задача минимум (MVP):**

1. **Количественный учёт — приоритет №1.** Сколько единиц на складе, в подготовке, продано, закуплено.
2. **Наполнение справочника товаров и склада** — параллельно с продажами и закупками.
3. **Упрощённые закупка и продажа** — прямой поток.
4. **Работа с неполными данными** — `NULL` для неизвестных цен/дат, но характеристики товара (жанр, издание, регион, год выпуска, год первого релиза) **обязательно** заполняет кладовщик.

**Задача максимум:** полная аналитика маржинальности, интеграция с API маркетплейсов, прогнозирование закупок.

## 5. Пользователи и роли

**На MVP один человек выполняет все роли.** Разделения интерфейсов нет, но роли выделяются в модели данных.

| Роль | Что делает |
|---|---|
| **Администратор** | Отвечает за работоспособность, миграции, справочники, технические операции. **Обязательно** |
| **Владелец магазина** | Смотрит аналитику, принимает решения |
| **Менеджер по закупкам** | Создаёт `purchaseOrders`, ведёт поставщиков |
| **Кладовщик** | Принимает посылки, заполняет характеристики товара (жанр, издание, регион, год выпуска, год первого релиза), оприходует, отпускает по продажам |
| **Менеджер по продажам** | Обрабатывает `salesOrders` с маркетплейсов |

**Почему администратор — отдельная роль:** кто-то должен отвечать за схему БД и миграции. В MVP — тот же человек, что владелец, но роль фиксируется явно.

## 6. Работа с неполными данными (режим миграции)

### 6.1. Два типа полей: обязательные и «восстановимые»

**Характеристики товара — обязательны для игр.** Кладовщик при приёмке **обязан** заполнить: жанр, издание, регион, год выпуска (`firstYearEdition`), год первого релиза (`firstReleaseYear`). На коробке эта информация всегда есть.

Для аксессуаров (геймпады, стилбуки) эти поля — `NULL`, это нормально.

**Цены и даты закупок — восстанавливаемые.** Если цена утрачена — `stock.avgCost* = NULL`. Не заменять нулём.

### 6.2. Флаг качества данных у товара

`goods.dataQuality`: `full` / `partial` / `minimal`.

| Значение | Что означает |
|---|---|
| `full` | Все обязательные поля заполнены, цены известны |
| `partial` | Характеристики есть, цен нет (типично для импорта) |
| `minimal` | Только имя и платформа |

### 6.3. Флаг «миграционная цена»

`stock.avgCostUpdatedAt = 2026-09-01` — цена внесена **вручную** (не из закупки). Служит флагом для интерфейса («товары для пересмотра»).

### 6.4. Режим «только количественный учёт»

Пока цены не восстановлены:
- **Количественный учёт — полностью** (задача минимум).
- **Маржинальность по товарам с `avgCost = NULL` не считается.**
- **`costAtSale = NULL`** — фиксируется как «себестоимость неизвестна». В отчётах — «нет данных», не портит средние.
- **Цены продажи запоминаются** — для будущей аналитики.
- Новая закупка с ценой «перетирает» `NULL` через средневзвешенную.

### 6.5. Восстановление старых цен

Администратор может **вручную установить `avgCost*`** для товара. Дальнейшие закупки пересчитают по формуле.

## 7. Мультивалютность

**При закупке** все три компонента — цена, доставка, **пошлина** — в валюте страны закупки (`purchaseOrders.currencyId`). Логика: пошлина зависит от стоимости товара в валюте, рублёвый эквивалент — производная.

**При приёмке на склад** — пересчёт в три валюты склада (RUB, USD, EUR) по курсу ЦБ на дату прихода. В `stock` — `avgCostRub`, `avgCostUsd`, `avgCostEur`.

**При продаже** — одна валюта (RUB).

**Списание себестоимости при продаже** — по **средневзвешенной**. `costAtSale` фиксируется на момент продажи, чтобы маржинальность не «плыла».

---

## 8. Два независимых контура

**Закупка и продажа не связаны напрямую.** Пересечение — только через `stock`:
- Закупка → `stock.quantity += N`.
- Продажа → `stock.quantity -= N`.
- Возврат → `stock.quantity += N`.

Это позволяет независимо развивать контуры, разделять аналитику и упрощает миграцию.

---

## 9. Минимизация персональных данных

**В `buyers` храним минимум:** `buyerNickname` (псевдоним с маркетплейса), `buyerCity` (опц.), `buyerAgeGroup` (опц., диапазон).

**Не храним:** ФИО, телефон, email, адрес, паспортные данные.

**Причина:** снижение риска ПД, отсутствие необходимости в дополнительной защите, снижение затрат.

**Свой сайт (SelfSite)** — отдельный контур с согласиями на обработку ПД. Не в MVP.

## 10. Технологический стек

|---|---|---|
| OLTP-СУБД | **PostgreSQL** | Стандарт для транзакционных систем |

| Документация | **Markdown** + **Git** | Версионирование, рендер на GitHub |

## 11. Принципы проектирования

1. **Справочники — отдельно от транзакций.**
2. **M2M — через промежуточные таблицы.**
3. **Имена — camelCase.**
4. **Деньги — `NUMERIC`, не `FLOAT`.**
5. **Заказы: закупка и продажа — две разные сущности.**
6. **`NULL` — «неизвестно», не «ноль».**
7. **Аудит — `createdAt`, `updatedAt`, истории статусов.**
8. **Работа с неполными данными — фича, не баг.**
9. **Минимизация ПД — принцип, не компромисс.**
10. **Комиссия маркетплейса — из отчёта, не угадывается.**

## 14. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Стартовое состояние | Работающий магазин, часть данных утрачена |
| Задача минимум | Количественный учёт + наполнение + упрощённые закупка/продажа |
| Обязательные характеристики игр | Жанр, издание, регион, `firstReleaseYear`, `firstYearEdition`, `audience` |
| Цены/даты | Могут быть `NULL`, `dataQuality`, `avgCostUpdatedAt = 2026-09-01` |

| Роли | Администратор + 4 бизнес-роли |
| Валюта закупки | Одна — валюта страны (цена, доставка, пошлина) |

| Списание себестоимости | Средневзвешенная (`costAtSale`) |
| Два контура | Закупка и продажа независимы, через `stock` |
| ПД | Минимум: `buyerNickname`, `buyerCity` (опц.), `buyerAgeGroup` (опц.) |
| Выплаты OZON | Пакетные (2 раза в месяц), `payouts` + `payoutAdjustments` |
| Комиссия | Из отчёта OZON (`payoutAdjustments`), не в `salesOrders` |

| Статусы | Только `purchase` / `sale`, без `common` / `collected` |
